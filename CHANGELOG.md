## [1.3.2] - 2026-11-20

**If you run Guardrails, upgrade; if your agents include Codex, also add its new hook entry.** A patch on 1.3.1. In a Codex session an approved call now runs when it is released, a Codex merge must carry its head pin, and the row says whether the call ran: this ends the 1.3.0 known limitation once you run `scripts/guardrails-install.sh --apply --codex` and restart each Codex session (see [Upgrading to 1.3.2](docs/UPGRADE.md#upgrading-to-132)). A slow GitHub read no longer uses up an approval, a gate check no longer holds the whole board, and a git read that does not answer no longer lets a call through. All were found in our own use; none is known to have been used against anyone.

### Security
- **Guardrails: a slow read at the release no longer uses up your approval, and nothing is written after the hook has stopped waiting.** At the release the board reads the PR head again. When GitHub was slow, the read ran out, and the approval was treated as if the head had moved. The gate was closed unused and the same call was filed again with no head on its row, after the hook had already given up. The agent was told "board unreachable".
  - **A pin in the command's own words now counts for every engine:** a `gh pr merge … --match-head-commit <the approved head>`, in the form the board writes, is released without a read. GitHub compares the head when the merge runs.
  - **An unread head is not a moved head:** one more read if there is time. Otherwise the approval stands, its grant is put back unchanged, and the agent runs the same command again. Only a head that was read and differs closes the gate, and an unread head never releases a call.
  - **A row filed while the PR cannot be read** is bound to the head the command pins, marked "not read", and never runs under a program go. Such a merge did run under a program go before.
  - **Past the hook's 8-second wait the board writes nothing** for the call: no release, no closed gate, no row, no task.
  - **The hook says "the board did not answer within 8 s"** when the board was slow. "Board unreachable" now means only that it could not be reached.
- **Guardrails: a gate check no longer holds the board, and a git read that does not answer no longer lets a call through.**
  - The gate service read git and GitHub one call at a time while holding the whole board, up to 8 seconds per read. Every other request, gate check and click waited.
  - A git read that timed out answered "nothing", and some calls were read as clear on that. For example, a push to a branch no rule protects, when the remote's address could not be read, ran unasked.
  - Every read of a check now runs in the background, with one 6-second limit for the check.
  - A call from an enforced agent that would be let through while a read ran out is held instead, and nothing is filed. With the board in observe or off mode, or for a caller the board only observes, it passes as before, with one observed line saying the reading may be incomplete. A PR or privacy read that runs out is "not read": no head is bound, and a program go does not approve it.
  - The same call sent twice at once is decided once: one approval runs once, and one row is filed.
- **Guardrails in a Codex session: an approved call runs when it is released, a merge is pinned, and the row says whether it ran.** This lifts the 1.3.0 known limitation once the new hook entry is installed.
  - **What changed:** Codex (checked on 0.162.1; the fix was checked again live on 0.170.0) takes only a "deny" from the gate hook. So an approved call went on to Codex's own prompt and ran whenever someone answered it. The approval was checked, and the row read "released", long before that. A merge also ran without its pin.
  - **The permission request:** the Codex hook file now also registers the gate script for Codex's `PermissionRequest`. The board answers "allow" only for the call it has just released (same agent, session, turn, tool, command and folder; once; within 30 seconds), never "deny", and nothing on any failure. An approved shell call then runs at once, with no second yes at the pane.
  - **The pin:** a Codex `gh pr merge` must end in `--match-head-commit <the PR's head now>`. Without it, or with a head the PR has moved from, nothing is filed and the agent is told the exact command to run. GitHub compares the head when the merge runs.
  - **The receipt:** a released Codex call's own result marks the row "ran". With none in 30 minutes the row says "no run seen" and Mission Control is told; a later result is still recorded, marked late.
  - **When you upgrade:** run `scripts/guardrails-install.sh --apply --codex` to add the entry, then restart each Codex session. Until then Codex asks as before. A held MCP tool call in a Codex pane can still meet Codex's prompt. Claude Code sessions are unchanged.

### Added
- **The board's one star toast can come at the first gate you approve.** The first time Guardrails holds something and you approve it, the board may show its one-time toast ("Zulu just caught an agent's merge before it ran"; merge, push, deploy, send and delete are named, any other class is "an agent call"), as it already could after a session it brought back or a closed task. It is still shown once, only when a repository address is set, and Star still only opens the repository page.
- **A scheduled job can send under its own name.** A name in `callerEvidence.jobs` (a launchd label mapped to a name) is now accepted as the sender of a message, a new task or a comment, but only when the board finds that very job behind the call. Any other process giving the name gets the "unknown agent" answer, as before. A name there that an agent, the owner or the board already has is refused as a sender, and the log says so once. It needs `callerEvidence.mode` `'observe'` or `'on'`; with caller evidence off, a job's name cannot be proven.

### Changed
- **The README leads with the gate.** It opens with what Guardrails does (a person approves before an agent merges, pushes, deploys or sends), then the board, with one line near the top and one after the Quickstart saying a star helps others find the project.
- **The light install and the demo: one line where the star question cannot be asked.** They ask the same one `[y/N]` question as before in an interactive terminal with `gh` logged in. Where it cannot be asked (output to a pipe, or no `gh` login), they used to say nothing; they now end with one line that names the repository and says a star helps others find it. It is printed once (kept in `data/star-prompt.json`) and never after the question. The full install is unchanged.

### Fixed
- **Mission Control comes back after a cmux relaunch with its contract.** When cmux relaunches and resumes nothing, the board restores each agent's session with `cmux restore`. cmux replays only the launch arguments it recorded, and for Mission Control that is the bare program, so it came back without its operating contract, its pre-approved tools, its model and its name. When it had no session record at all, it was not restored, and nobody was told.
  - **What it does now:** Mission Control's pane gets `scripts/mc-resume.sh <id>` instead, run from the board's checkout. The id is the one Mission Control recorded in `data/mission-control-session-id`. It must be a strict UUID with a transcript in that checkout's project folder. A newer session for the same workspace in the hook map wins only under the same two conditions.
  - **When:** only into a fresh login shell, once per cmux launch, and never while that session runs anywhere. The resume picker is answered only when it is on screen, and a trust dialog never.
  - **Otherwise:** one ticker line and one desktop notice say Mission Control was not resumed, and why.
- **Docs: auto-login after a password change.** INSTALL's power chain now says to check `/etc/kcpassword`. macOS deletes that file when the account password changes (some updates delete it too), and the Mac then waits at the login screen with auto-login still set.
- **The gate integrity check no longer stalls the board.** Its git reads ran one after another while holding the whole board, up to 3 seconds each, and a first check after a restart could hold it for minutes. Web requests, gate checks and the check of who is clicking all waited. The reads now run in the background, with one 5-second limit for the whole check. A read that is slow or hangs never turns the card red by itself. The card keeps its last full reading for three polls, saying it was not checked, then turns amber. It turns red only if no full reading has come in by the usual behind time. A red that is showing stays red. A read slower than a second is logged with the program's name only.
- **Sessions that dropped out of the hook maps come back after a cmux relaunch.** When cmux relaunches and resumes nothing, the board restores each login shell from the agents' hook maps. A session missing there (seen for two residents, silent in the maps for weeks) was passed over with no line, and its pane stayed a bare shell for days. Now the board takes cmux's own record of the workspace instead, with the same checks: a well-formed id, not a `--profile` launch, its session not running in any process, and never for a closed directory entry. Every login shell it passes over gets one log line saying why. A registered resident still at a bare shell after the 2-hour window is not restored on its own. It gets one low task to Mission Control per cmux launch, with the facts (hours bare, the last session written, the tasks it owns, the restore line), and one ticker line a day that names that task. A board restart files no second task, and a task closed or cancelled keeps that launch quiet.
- **Names enforced: a mapped job is recognised on its first call.** The board kept "not running" for a mapped job for 30 seconds, so a job that started in that window was not recognised: under `callerEvidence.mode: 'on'` its messages went out marked UNVERIFIED and its ledger steps were refused (the second known limitation of 1.3.0). A running job is still kept 30 seconds; "not running" is no longer kept, and the labels are asked together. And a kept job's process id now names a process only while that process's start time matches the one seen when it was kept (within 2 seconds), as for sessions: a process that got the same id after the job ended was taken for the job.
- **Docs: Codex panes come back after a reboot.** `docs/CMUX-SETUP.md` said Codex panes are not resumed and must be resumed by hand. The board restores them as it restores Claude ones, when a cmux relaunch leaves login shells: it says now when, what is left to you (a session started with `--profile`, a pane still a bare shell after two hours) and what to run then.
- **The test suite no longer fills the temp folder.** Most test files made temp folders and left them, about 2,300 per full run (on one Mac, five weeks of runs left about 231,000 folders and 31 GB). Every test file now imports `test/temp-root.mjs` first: it gives the test process one temp folder (`TMPDIR`, so the processes a test starts use it too) and removes it when the process ends, also after a throw or a signal. `KEEP_TEST_TMP=1` keeps it and prints where it is. A test fails when a test file does not import it first. `scripts/chat-intake-install.sh` and `scripts/state-backup-install.sh` now remove their own temp folder, as the guardrails installer already did.
- **Guardrails: the Codex refusal text named a form it refuses.** When a held Codex call's folder is not named, the call is refused without a row and the agent is told how to restate it. That text offered "an absolute script path", which the same rule refuses on purpose, so an agent that followed it was refused again. The text now names only the forms that are read (`cd /abs/path && …`, `git -C /abs/path …`, `gh … --repo owner/name`), and a test files one call in each form it names. Nothing that was held is now let through. In 1.2.2 to 1.3.0.
- **Guardrails: a refused merge left an empty task.** A Codex merge with no pin of its own is refused without a row. When the caller had no live task (a headless run, a session nobody registered), the board had already made a task for the row, so an empty task with no gate was left for Mission Control. The task is now made only once nothing else can refuse the call. What is held, refused or filed is unchanged.
- **Agent Mesh: a Codex pane left scrolled up.** With its footer reading `enter/esc latest`, the pane read as "not recognised", so messages to it queued until they expired. Typed text and one Enter submit in that view, so it now reads as ready.
- **The test suite in a public checkout.** One test added for the Codex refusal text read the Guardrails page at the path it has in the source repository, so in a clone of this repository it failed with "no such file". It now reads `docs/GUARDRAILS.md` there.

## [1.3.1] - 2026-11-15

**Upgrade if you installed Node from somewhere other than nvm or Homebrew on Apple silicon, or if you run Guardrails.** A patch on 1.3.0: the installer could refuse a working Node, and one form of an approved merge ran without its head pin under one shell. The known limitations of 1.3.0 (below) still apply.

### Security
- **Guardrails: a merge written with `&>` is no longer pinned.** When you approve a held `gh pr merge` that is the only command of its call, the gate appends `--match-head-commit <the head you saw>`, so GitHub refuses if the pull request moved. With the output sent through `&>` or `&>>`, bash and zsh read one redirect, but dash reads `&` (run in the background) and then a redirect: the pin became a second command and the merge ran unpinned. Such a merge now has its head read again before it is let through, like every other form the gate cannot pin; `2>&1` is unchanged. Only a session whose shell is dash was affected (`/bin/sh` on Debian; on macOS, `/bin/sh` runs bash unless its owner changed it). In 1.3.0, the first release with the pin. Found in our own review; not known to have been used.

### Fixed
- **The installer on a Mac with Node in `/usr/local/bin` and no nvm.** `scripts/env.sh` fell back to `/opt/homebrew/bin` without checking that Node was there. With Node from Intel Homebrew or the official installer, `./install.sh` said "Node >= 22 required (found: none)" with Node 22 installed, and the scripts that start Node by its path (`scripts/guardrails-install.sh`, `scripts/guardrails-anchor.sh`, the board's start script, triage) could not start. It now takes the first folder that holds an executable `node`: nvm, then Homebrew, then `/usr/local/bin`, then the `node` on your PATH. In every release before this one.
- **The test suite on Linux and on a nearly full Mac.** The repository's Linux test job failed on 1.3.0: seven tests, the two causes above. And one first-hour test judged the disk and memory cards of the machine it ran on, so on a Mac with a nearly full disk an upgrade's test step failed and the upgrade rolled back. That test now leaves those two cards out.

## [1.3.0] - 2026-11-15

**Security: if you run Guardrails, upgrade.** In 1.2.4 and every earlier release, a held action could run without asking you in other spellings: a held call behind a launcher's flag that takes a value (`timeout -s KILL 5 …`, `caffeinate -t 5 …`, `noglob …`, `stdbuf …`); and in-place edits inside a guarded folder (`sed -i` after a `cd` there, `plutil -replace`). And the dry run the gate asks for before a write was itself taken on trust: a script that pays or sends without its flag would have run as "the dry run". Two more spellings, an interpreter named with its version and a held program run through its interpreter by its file, were patched in 1.2.4 the day it was found; they are in 1.2.3 and every earlier release, and this release reads more of them than the patch could. All were found in our own review; none is known to have been used. The details are under Security below.

Trust and reach. An approval is bound to what it refers to (the PR head, the pushed commit, the content of the scripts a call runs). The gate reads more of what an agent can do (a session it starts for itself, runners, MCP tools, writes through `gh`, the desktop, another pane), and those new checks ship in `observe`: they report what they would hold and change no answer until you turn them on. The scheduled triage pass is cut down to two tools and a short list of exact calls. And the first hour is lighter: the one-line install does four things and asks for nothing that costs money.

**What to do when you upgrade** (the long form is in [docs/UPGRADE.md](docs/UPGRADE.md#upgrading-to-13)):
- **Your rules file is never changed by an upgrade.** The rules this release adds (an agent running the installer, the new classes, the eight more gate modules, the list of checks) reach `overlay/policy.json` only when you copy them from `examples/policy.json`. The guardrails card says how many are missing.
- **Run `scripts/guardrails-install.sh --apply` once more.** It adds `"onFailure": "block"` to the two blocking hook entries (without it, a gate hook that cannot start lets every call run) and, on an install from 1.0.x, the settings-change hook. It needs Claude Code 2.1.295 or later.
- **Triage:** an install made before 1.3 keeps starting workers by itself until you add `triage: { dispatch: 'ask' }`; and if you keep your own `overlay/config/TRIAGE.md`, copy the example's steps, because the pass can no longer run the `curl` lines of the old one.
- **An approval you gave just before the upgrade and the agent has not used yet is asked again**, and approvals that ran out unused in the past are marked expired at the first start, with one ticker line that counts them.
- **A checkout reached through a symbolic link:** run the upgrade from the real path (`cd "$(pwd -P)" && ./install.sh upgrade`), or use the board's UPDATE button or `zulu upgrade`. The fix for this is in this release, so the release you upgrade from does not have it.
- **`./install.sh` with no word is now the light install.** If a script of yours relied on it doing everything, it wants `./install.sh --full`.

### Security
- **Guardrails: the two readings of 1.2.4, and what that patch could not carry.** 1.2.4 reads an interpreter or a shell named with its version or build as the plain one (`python3.13`, `pypy3`, `node22`, `bash5`, `zsh-5.9`, `csh`, `tcsh` …), and reads a held program that is itself a script when it is handed to its interpreter by its file (`node /opt/homebrew/bin/vercel deploy --prod`, `bash bin/zulu upgrade`). This release has both, and reads three things more that 1.2.4 lists as not read. A program word that is a variable given one fixed value in the call is read by that value (`I=sh; $I ./bin/zulu init`, and `PY=python3; $PY - <<EOF`, whose program text is then read for a held action). The script on a shell's input with its words before the file is read (`bash -s upgrade < bin/zulu`). And the `zulu` program handed to `eval`, `xargs` or `watch`, or echoed into a shell, is held (`eval "zulu upgrade"`, `echo upgrade | xargs zulu`, `echo "zulu upgrade" | bash`). With `runners` or `renamedBins` at `enforce` a versioned name is also still read as an unknown program, so a few forms are held under it where the plain name is clear. A shell's syntax check of a held program's file (`bash -n bin/zulu`) is held, as in 1.2.4. **Still not read, and said in [docs/GUARDRAILS.md](docs/GUARDRAILS.md):** a program in a language the gate does not parse (`lua`, `tclsh`, `awk`, `Rscript` and the like), and an interpreter kept in a variable that the call gives two values. Nothing that was held before is freed.
- **Guardrails: a word in front no longer hides a held call.** A wrapper's flag that takes a value (`timeout -s KILL 5`, `caffeinate -t 5`, `sudo -D <dir>`, `exec -a x`), zsh's `noglob` and `nocorrect`, and plain launchers such as `arch` and `stdbuf` were read as the program, and the gated call behind them passed. They are looked through now. This part is a fix, not a switch. `eval`, `xargs`, `watch`, `ssh <host>` and `parallel` in front of a deploy, and a deploy run by `find -exec`, are read too; before, they were held only when the call behind them carried a gated word such as `merge` or `push`. More value flags are skipped in every mode (`sudo --user root`, `arch -arch arm64`, `env -P <path>`, `time -o <file>`).
- **Guardrails: the dry run a write form asks for is never a held call, and a script can name its own dry flag.** For a script run with a write flag (`--live`, `--commit` …), the gate asked for "the same call without the flag" first. That assumes the flagless run changes nothing. Seen on one board: a runner whose flagless run still pays (its preview is `--quote`) was asked for exactly that, with `--yes` kept, and the run would have counted as the dry run. Now the dry form is read by the same rules before it is offered; if it is held too, no dry form is asked for and the gate goes to you as it stands, its row saying `dry run: NONE` and why. `dryForms` in the policy names a script's own dry flags, which the dry form then carries (before a `--`, where the script reads options). The hint also tells the agent to run it only if the script's help says it changes nothing. A script that pays or sends without its flag belongs in a class of its own with its preview flag on `unlessFlags` ([docs/GUARDRAILS.md](docs/GUARDRAILS.md)). A fix that comes with it: a freeing flag (`unlessFlags`, `@dryFlags`) now counts only before the first `--` after the script or program; after it, the script reads it as an argument and runs its held form.
- **Guardrails: inside a write-guarded folder.** After `cd ~/Library/LaunchAgents` (or with the call made from there) `echo hello` and `printf` with no redirect were held, because their words were read as files in that folder; `sed -i "" … <file>` there was not held, and `plutil -replace`, `-insert`, `-remove`, `-convert` and `-extract` were held nowhere. The words of `echo` and `printf` are now text, the in-place `sed` form is held as it is with the full path, and the writing `plutil` options are held in both forms; `plutil -p` and `-lint` stay free.
- **Guardrails: an approval the agent never used no longer stays approved.** A gate you approved and nobody ran kept the status `approved` after its time was over; the board looked at it again only if the same call came back. The check that releases a call read the grant's own time and, with the receipt chain on, the chain, which still held that approval. So one grant written by hand into the board's state folder, naming such a gate and giving itself a new time, let a held call run once, with no edit of the task record and no restart. Writing that file is itself a held action, so this was a second line, not an open door. Two changes: the board now marks a run-out approval `expired` when it starts and with every poll, on open and closed tasks (the task gets `GATE gN expired unused`, the chain gets its line, nobody is woken); and a grant is released only while the task's own record says the gate is approved and still in time. Otherwise nothing runs, the ticker says `REFUSED … a grant was presented …` in red, and the call is asked again. A hand-made grant for a gate that already ran or was never approved is refused the same way; it used to end in an error. After the upgrade the first start marks every approval that ran out in the past, with one ticker line that counts them.
- **Guardrails: a gate hook that cannot start stops the call.** The installer writes the gate hook before a tool call and the settings-change hook with `"onFailure": "block"`. Before, a hook whose script was gone, or that Claude Code timed out, let every call run: the registration stayed and nothing was asked. Run `scripts/guardrails-install.sh --apply` again to get the field on an existing install; the guardrails card says which entry lacks it until then. **Before you move or delete the checkout, run `scripts/guardrails-install.sh --remove --apply`**: with the script gone and the entries still registered, every tool call is blocked. See [docs/GUARDRAILS.md](docs/GUARDRAILS.md#install).

### Added
- **Guardrails: an approval is bound to what it refers to.** A merge gate records the PR's head commit and shows it on the row; the approved merge runs pinned to that head (`--match-head-commit`, added by the hook), or the board reads the head again when it cannot pin. A push gate records the commit every pushed ref points at, and says so on the row when a push names no fixed refs (`--all`, `--mirror`, `--tags`). The pin is used only when the shell would hand it to the program; on a line that ends in a comment, a semicolon or an ampersand the head is read again. The fingerprint (`gate-v3`) includes the content of the scripts a command runs. If any of them moved after you approved, nothing runs: the gate is closed as superseded and the call is asked again, saying what moved. A `GH_REPO` set in the agent's shell is passed to the board, so the row and the program-go check are about the repo `gh` will act on. One effect of the new fingerprint: an approval given just before the upgrade and not yet used is asked again.
- **Guardrails: a script changed inside the call that runs it is refused.** The content of the scripts a held call runs is read when the gate is filed and again when the approval is used: both before the call runs. A call that first changes the script (`sed -i … x.mjs && node x.mjs --commit`) would be released and then run the changed file. Such a held call is refused and not filed, with the step to take: make the change as its own call first, then run the script alone. A dry run in a call that changes the script first no longer counts as the dry run.
- **Guardrails: a push or merge whose commit the call itself can move is not bound, and its row says so.** A held push or merge is bound to the commit (or PR head) read when it is filed, before the call runs. When the same call first switches branch, commits, pushes (before a merge), changes the PR with `gh`, writes a file or runs a script, the row would name one commit and another one would go up. Such a push or merge carries no binding, and its row says what runs before it ("this push is not bound to a commit (run before it in the same call: git switch, git commit)"); the approval is of the call as written, used once. The agent is told how to get a bound row: run what comes first as its own call, then the push or merge alone. Commands that move no ref and write no file (`git status`, `log`, `diff`, `add`, `fetch` without a refspec, read-only `gh` verbs, `echo`, `cd` …) keep the binding. A `gh pr merge` with no PR named after a branch change in the same call is refused and not filed: name the PR.
- **Guardrails: a session an agent starts for itself is read (`engineStart`, ships in `observe`).** A child session started with settings of its own can run with no gate hook at all. The new check reads `claude` and `codex` started from an agent's shell: every headless start gets a reading, and at `enforce` the forms that leave the hook out or stop the session asking are held in a class of their own (`--setting-sources` without `user`, `--settings`, `--bare`, the skip-permissions and bypass modes, another config home set for the call). A plain start is never held. See [docs/GUARDRAILS.md](docs/GUARDRAILS.md) for what this cannot see.
- **Guardrails: runners (`runners`, ships in `observe`).** A program no rule names, with a gated call among its words, is held under that call's class: `npx vercel --prod`, `uv run gh pr merge 3`, `op run -- …`, `docker exec c …`, `nix-shell --run "…"`. No list of runners is kept. `node scripts/gate-replay.mjs` now also prints the first word of each call it would newly hold.
- **Guardrails: MCP tools are held unless they are known reads (`mcpDefault`, ships in `observe`).** A tool a rule names is held under that rule's class; a tool on the read list (`lists.mcpRead`, plus names that start with `get`, `list`, `search` and the like) passes; anything else is held as "an MCP tool nobody has classified". The wider MCP rules come with it: all send, reply, forward and schedule forms, store tools, and generic write names under a new `remote-write` class. The board records every tool it is shown in `mcp-seen.json`, files one low task per server and day for new unclassified names, and keeps an allow file so a known read never starts Node. A known tool that arrives from a different source is held. `node scripts/mcp-review.mjs` prints what has been seen and a starting list. The hook's shell step takes a tool's name from the input only when it stands there once, and the board checks its allow file against the copy on disk. A graphql call whose body comes from a file or a pipe is held as unreadable. `gh gist create`, `gh repo create --public` and `gh pr review` are held, and so are comments, issues, pull requests and edits on a repo of your `publicRemotes` list.
- **Guardrails: `gh` and SQL writes (`remoteWrite`, `observe`).** `gh api` with a write method, fields or a mutation, `gh workflow run`, `gh release create/delete/edit`, `gh pr close/ready`, `gh issue close/delete`, `gh repo edit/archive/rename`, and SQL `UPDATE`, `DELETE`, `INSERT`, `ALTER`.
- **Guardrails: typing into another pane (`paneReach`, `observe`).** `cmux send` or `send-key` aimed at another workspace or surface, a new cmux workspace or split started with a command, and `tmux send-keys`, by any agent other than Mission Control. It is there to be read: the text arrives in the other pane looking typed.
- **Guardrails: a `desktop` class (`desktop`, `observe`).** Tools and commands that drive the desktop or a browser: computer use, the browser extension, `cmux browser click/type/eval`, `osascript` UI scripting, `cliclick`. It is a standing class: a program go on the task covers it, but never an action aimed at this board's own page.
- **Guardrails: four more forms for `selfProtect`.** `git sparse-checkout set` / `init` in the live checkout; the live repo's git dir named with another work tree; a write target that starts with a command substitution in front of a gate file's path; and a variable set in the same call as the write target (`F=src/gates.mjs; echo x > $F`). The check still ships in `observe`.

The call is read by its first word, as the installer reads it, so a freeing word added later (`--yes --help`) frees nothing. `check`, `verify`, `doctor`, a plain `backup`, the demo, help and a dry run of either install stay free, and so does another project's `install.sh`. `backup --with-secrets` is held too. If you keep your own `overlay/policy.json`, copy the three rules from `examples/policy.json`.
- **Guardrails: naming the product does not hold a call.** The installer program's name is also the product's name. The three installer rules on the program say `nameIsWord`: the fast path's line for the name only sends the call to the rule, which reads the parsed command, so a note title, a folder or a report line that says "Zulu" holds nothing. A run of the program is held: plainly, behind `env`, `sudo` or `timeout`, by its path, in a shell's own text. A call that keeps the name in a variable is held as unreadable where that value can become the program (a variable in program position, `eval "$X"`, a shell fed from a pipe). Held as the same forms of a push are: the program among the words of `eval`, `xargs`, `watch`, `npx`, `su -c` or `trap` (read by its rules whatever the `runners` switch), a shell fed from a pipe in a call that names it (`echo "zulu init" | bash`), a substitution in program position that names it (`$(echo zulu) init`), an alias given it, and a variable in program position whose fixed value is the program (`export Z=zulu; $Z init`). **Not held, and said in [docs/GUARDRAILS.md](docs/GUARDRAILS.md):** a run of the program from inside a program the gate does not read, a heredoc program or an inline body (`python3 - <<EOF … subprocess.run(["zulu", "init"])`). `zulu upgrade` and `zulu rollback` are held as in 1.2.
- **Guardrails: the gate-code list has every module the gate loads.** The list (`gateCode`: the files `selfProtect` guards in the live checkout and the integrity card compares with the remote) named the files somebody had thought of; the receipt chain, which decides whether an approval may run, was not among them. It now has every module the gate service and the two hook programs load (eight more: the receipt chain, the row context, the private-file and secret-text helpers, the profile, the completion packet, the upgrade and the worktree modules), and a test follows the imports and fails when a new one is missing. An install with its own `gateCode` list in `overlay/policy.json` adds the eight lines itself ([docs/INSTALL.md](docs/INSTALL.md#7b-upgrading)). The card's file check now reads a file newly on the list at once; it kept what it had read for the old list until the board restarted, and showed the new file as changed.
- **Guardrails: a settings file that points git at another repository is refused, and shown on the card.** A settings file's `env` block reaches the shell every tool call of a session runs in (seen in scratch folders on Claude Code 2.1.321: with `GIT_DIR` there, git answered from one folder with another repository's address; the same from the environment a session is started in, from `~/.zshenv`, and in Codex 0.162.1). The board reads a call's repository by its folder, in its own environment, and sees none of it. Now a settings file whose `env` block sets `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_NAMESPACE`, `GIT_CONFIG_COUNT` (with its `GIT_CONFIG_KEY_n` and `GIT_CONFIG_VALUE_n`) or `GIT_CONFIG_PARAMETERS` turns the guardrails card red (your own settings file, each registered agent's project and local file, and the settings a session was started with), and the settings-change hook refuses such a change in a running session. The value is never shown. `GIT_SSH_COMMAND`, `GIT_SSH`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_NOSYSTEM`, `GIT_PROXY_COMMAND` and `GIT_EXEC_PATH` (a deploy key, a proxy, a settings file of your own) are a note on the card without colour and are not refused. The guarded list gains `~/.bash_login` and git's second settings file `~/.config/git/config`, beside the shell and git start files already on it. **Not covered, and now said in GUARDRAILS.md:** the same variable in the environment a session is started from or exported by a shell start file is not read by the board; holding a git call when one is set is a later release.
- **Guardrails: the card reads the settings each session was started with.** Claude Code takes one more settings source on its command line (`--settings`, a file or JSON text), ranked above your own, the project's and the local file; cmux starts every session that way. `disableAllHooks` there silences the gate hook from the session's first call, and nothing read it. With gate integrity on, the guardrails card now reads the command line of every running Claude Code session and every file in the folders such files are kept in (`gateIntegrity.startSettingsDirs`, by default cmux's own), and is red on the same two things as for the other settings files. The folder is a guarded path in the shipped policy. See [docs/GUARDRAILS.md](docs/GUARDRAILS.md#the-gate-checks-itself).
- **Guardrails: anchor the hook in managed settings (optional).** `scripts/guardrails-anchor.sh` shows the installer's hook entries as a managed-settings drop-in and prints one line for you to type with your password. Managed settings are read by every session, including one started with your settings file left out, and cannot be switched off from a user or project file. The script itself never runs with administrator rights; the line checks the file's hash on the copy before it goes live. `--check` says whether it is anchored, `--remove` prints the line that takes it out. See [docs/GUARDRAILS.md](docs/GUARDRAILS.md#anchor-the-hook-optional-your-password-once).
- **Chat intake: a quiet channel.** `"quiet": true` on a channel in `config/channels.json` is for one where people also just talk. Its requests are still filed and get the 👀 reaction, but there is no "Filed as" reply and no line when the task is closed as chatter ([docs/CHAT-INTAKE.md](docs/CHAT-INTAKE.md#setup)).

With `curl` gone and its writes scoped (below), that was the one way left from the unattended pass to a session with every tool, through a prompt file the pass wrote from text on cards. A task that came from outside the board (chat, GitHub) shows where it came from, not its title. The example procedure (`config/TRIAGE.md`) reads it in step 1. Your own `overlay/config/TRIAGE.md` keeps its step 1 until you change it (the old readings still work, at a higher cost).

Seen on Claude Code 2.1.321: a curl to another address, to the board's other readings, and one behind `&&` were refused. Report names now carry the time in UTC. If the list cannot be built, the pass does not start. Not bounded by the list: read-only shell commands, which Claude Code runs without asking. As in 1.2.3, the three start-line flags are passed only when `claude --help` lists them. Your own `overlay/config/TRIAGE.md` keeps its curl steps until you change it, and with this list those steps are refused: copy the example's.

With no Read tool it cannot write over any existing file, so it can no longer rewrite the scripts on its own list. Seen on Claude Code 2.1.321: that path was written, other new paths were refused. Reads of the cooldowns and the reading go through the board script.
- **The scheduled triage pass reads only your user settings.** It runs from the checkout, and a headless run also applies the allow rules saved in the checkout's `.claude/settings.local.json` (the "Yes, and don't ask again" answers given in sessions started there). Seen on Claude Code 2.1.321: a saved `Bash(curl *)` let the pass run a `curl` that its own list does not name. `scripts/triage.sh` now starts it with `--setting-sources user`; with it, that call was refused, and the gate hook, which lives in your user settings, still ran.
- **The scheduled triage pass no longer ends a running job.** Its restarts were `launchctl kickstart -k`, which ends a running instance first. A job card reads `due` while its slot has passed and its grace has not: a long job still running then reads `due`. Seen on one board: a pass restarted a long job shortly before it would have finished. The list now holds `launchctl kickstart` without `-k`, which starts a job that is not running and leaves a running one alone, and the example procedure (`config/TRIAGE.md`, step 3) names the reading's statuses in two groups: a card that reads `due`, `warn`, `amber`, `unknown` or `info` is reported, never acted on (a threshold or a queue for a person had become an ask for a worker), and a fix or an ask is only for `down`, `red`, `error`, `failed`, `overdue` or `stale`. A restart is only for such a job, and a container restart only for a container that is down. With `--setting-sources user` the pass has no project instructions, so every rule it needs is in the procedure. Your own `overlay/config/TRIAGE.md` keeps its step 3 until you copy the three new lines from the example.
- **The scheduled triage pass is told which calls its tool list allows.** The pass runs with a fixed list of programs (`scripts/triage.sh`), and a call outside it is refused. The example procedure (`config/TRIAGE.md`) now says: one program per call, with no `cd`, `&&`, `;`, `|`, `$(…)` or variable in it; answers taken as they come, since filter programs are not on the list; a long saved answer read with the Read tool; nothing kept in the temp folder. Seen on one board over four days: a pass had 1 to 14 refused calls (most often a `curl` piped into a filter, or a `cd` in front). It always found another way, but each one cost a round. The kickstart line had `gui/$(id -u)/…`, which the list refuses; it now reads `gui/<UID>/…`. `scripts/triage.sh` writes your user id in, for `<UID>` and for the older `$(id -u)`, as it hands the procedure to either engine, so an install set up before this change is fixed by the upgrade, with no edit of your `overlay/config/TRIAGE.md`. `zulu setup` also fills it into that file along with your name. `scripts/triage.sh --print-prompt` shows the procedure as the pass gets it.
- **Workers and residents are told how a held call works, and triage keeps task titles out of its commands.** A worker's brief footer and a resident's launch brief now say what to do when Guardrails holds a call: set the task's focus first, wait for the owner instead of retrying or rewording, and run the approved command once. They also say to write notes with the edit tool, since a heredoc that names a gated word cannot be read and is held. The example triage procedure (`config/TRIAGE.md`, step 6) now writes its summary to a file and sends that file, instead of putting the summary in a shell command. A summary is built from task titles, and a title that names a gated action made the scheduled pass's call unreadable; with Guardrails enforcing, that call is refused with nobody there to answer it.
- **The one-line install is light.** `./install.sh` (and the `curl … | bash` line) now does four things: a Node check, your config, the board as one LaunchAgent, and it opens the board. It installs no Homebrew package, writes nothing to your Claude settings and loads nothing that costs money. Before, it installed ten tools, loaded a scheduled triage job that runs a model four times a day, and merged hooks into your Claude settings, after one question. All of that is still one command: `./install.sh --full` (or `| bash -s -- --full`). A re-run of either adds what is missing and removes nothing.
- **Your sessions without cmux.** On a Mac where cmux has never run, the board shows your live Claude Code sessions from Claude Code's own registry, with the context gauge, read-only.
- **A next-steps card in place of a setup prompt.** A light install shows one info card with what you can add, each as one command: Guardrails, the full install (it says that triage costs money), the brain, what to watch. Guardrails on a light install (`./install.sh --guardrails`) adds the gate and leaves the board as it is: the sessions and cards you see stay, and no `--switch` is asked for.
- **`zulu setup` requires four steps:** GitHub, an engine, who you are, and the final check. What to watch, alerts, the vault, the brain, macOS tuning and residents are optional; skipping one no longer leaves the setup card amber.

The Guardrails card appears once its hook is registered, a gate exists, or the rules file is invalid, and from then on it stays (the board marks the install's state file), so a hook that is lost later reads MISSING as on any board; the cmux card appears once cmux is there. Running the full install on a light one ends this: the state file then says full, the cards are a full board's, and upgrades run the full install's steps. And the install step of an upgrade writes only the board's plist again on a light or a Guardrails-only install; the full bootstrap it ran before would have added cmux config, a secrets file and a socket password to an install that had none.

### Fixed
- **`./install.sh upgrade`, `./install.sh rollback` and `node scripts/migrate.mjs` did nothing under a linked folder.** Both scripts decided whether they were the program being run by comparing the path as typed with their own real path. In a checkout reached through a symbolic link (a linked home or projects folder, `/var` and `/private/var`) the two differ, so the main block was skipped and the command ended at exit 0 with no output: no upgrade, no rollback, no migration, and nothing said so. Both now resolve links first, as every other script already did, and a test fails when a script compares the unresolved path. The board's UPDATE button, the `zulu` command (it resolves its own path first) and the migration step inside an upgrade or a restore were not affected: they start the script by its real path or call it directly. **1.2.4 and earlier have this, so it applies to the upgrade to this release:** in a checkout reached through a link, run the command from the real path, `cd "$(pwd -P)" && ./install.sh upgrade`.
- **Deciding a gate no longer drops a question that was already waiting on you.** When a task was blocked on you (a question to you on the ledger) and a gated command then waited on the same task, your decision on the gate removed you from the task's "waiting on" list. The task read blocked with nobody named, and the question left your waiting list while it was still open. Now a gate takes away only its own wait: a question filed before the gate, or one filed while the gate waited, stays until it is answered. A task never reads blocked with nobody named after its gates settle.
- **Guardrails fix: the page folder's trigger line is a path segment.** The fast path's line for the board's own page folder was the bare word `public`, matched anywhere in a call and in the folder it was made from. Every call that merely contained the letters (a checkout in `…/zulu-public`, a word such as `publicRemotes`) started the hook's Node step, about a tenth of a second slower, and in a checkout under such a path three hook tests failed, so `./install.sh verify` and a one-click upgrade's test step failed there. The line now matches the name only as a whole path segment (`public/app.js`, `cd public`, `-C public`, a call made from inside the folder). What is held is unchanged. A folder named exactly like a gated word still sends its calls through the Node step; [docs/TROUBLESHOOTING.md](docs/TROUBLESHOOTING.md) says what that means. `node scripts/gate-replay.mjs --lines-before <trigger file>` counts how many recorded calls an older trigger file routed and today's lines do not.
- **The guardrails card after a restart.** The card is computed at the end of each poll and the page reads it at the start of the next, so the first page after a restart showed the card the previous process had left behind: after an update it could still say "behind" for one poll. A new process now computes the card once before it starts answering (and waits at most 3 seconds for it). In the Guardrails-only profile the card now also carries the gate-integrity reading when that check is on; it was computed there without it.
- **Names enforced (`callerEvidence.mode: 'on'`, still off by default): three corrections before anyone turns it on.**
  - A task filed by a caller the board could not verify kept the declared name as its requester, and the only mark was one comment, which a long task trims away. The mark is now a field of the task (`unverified`), read by `task.sh show`, the WORK row and every wake about the task. The declared name has no requester standing on such a task and gets no requester wakes until you confirm the request on the board, or Mission Control does with `task.sh confirm-request <id>`.
  - Evidence could lower a hold: a hook that declared an enforced agent was only observed when the board found a session it did not know behind the call. A call is now held when either the declared name or the session found is enforced.
  - `mesh-cli.mjs outbox drop <agent>` took no name, so any local process could remove a queued message, a gate decision included. It now needs a name the process backs (the addressee, Mission Control or you for everything, a sender for its own). In every mode the log and the ticker say who dropped what.
- **Chat intake: a plan-first task's assign line after you approved the plan.** When a task from a plan-first person was assigned after you had approved its plan, the line typed into the agent's pane still said "PLAN FIRST: no work until … reviews; post it with task.sh plan". An agent that followed it would post a second plan and put the task back on you. It now says the plan is approved and to work to it, and says PLAN FIRST again only while a later plan waits for your review or after you declined one.
- **Chat intake: a channel the bot is not in no longer fails every history sweep.** A routed channel the bot had not been invited to answered the five-minute catch-up with `not_in_channel`, which failed the whole sweep: the channels after it were not read and the link card would have turned red. That channel is now skipped, said once in the log, named on the link card ("not readable: #… (invite the bot)"), which stays amber until the bot can read it, and read again on every sweep, so an invite is picked up without a restart. Its catch-up starts from the first skip, never further back. Also fixed: the intake's status file could read "connecting" while the link was up (two writes on the first frame; the older one could land last). Status writes now land in order.
- **Tests: the board-down hook test no longer depends on one git start under a second.** With the board down the hook reads the repository itself and gives each git read one second; a read with no answer counts as not read, and the call is held. On a loaded machine that made the test's "this form passes" line fail once in CI. The pass form now gets up to three tries, and a new test pins the direction: a repository whose reads never answer is held, not passed, and the hook still answers inside its own deadline. The hook is unchanged. The troubleshooting page has a row for the same thing seen by hand.
- **Tests: a board a test starts gets its port from the system.** Seven tests picked a port at random from a fixed range of 40 to 900. Two suites running at once on one machine could pick the same one: the second board could not listen, and its test talked to the other suite's board or waited for nothing. One suite alone was not affected. They now ask the system for a free port, and a test names any test that guesses one.

### Known limitations
- **Guardrails in a Codex session: an approved call still stops at Codex's own prompt, and the approval is checked when it is released, not when it runs.**
  - **What happens:** Codex (checked on 0.162.1) accepts only a "deny" from the gate hook. When you approve a held call, the hook lets it through, and Codex prints `Hook failed … unsupported permissionDecision:allow`. Codex then shows its own "Would you like to run the following command?" prompt, as it does whenever a call asks to run outside its sandbox, which most held calls do.
  - **What is checked, and when:** the gate checks the approval once, when it releases the call: the PR head, the pushed commit, and the content of the scripts the call runs. The call runs only when someone answers the Codex prompt, which may be much later, even beyond the approval's 120 minutes. A change made in between is not seen. The pin that makes GitHub compare the head at the moment of a merge does not apply in Codex. The approval is already used, so a "no" at that prompt leaves a row that reads as released.
  - **What to answer:** at the Codex prompt, answer **"Yes, proceed"**, soon after you approved. Never answer **"Yes, and don't ask again"**: it saves a Codex rule, and Codex then never asks for that command again. The gate still holds that command in a session it enforces, but in a session it only observes, nothing asks at all.
  - **The fix is planned for the next patch.** The gate will answer Codex's own prompt only for the call it has just released, so approval and run happen together again, and a merge from Codex will have to carry its own `--match-head-commit`. See [docs/TROUBLESHOOTING.md](docs/TROUBLESHOOTING.md#guardrails). Claude Code sessions are not affected.

## [1.2.4] - 2026-11-14

**Security: if you run Guardrails, upgrade.** In 1.2.3 and every earlier release, an agent could run a held action without asking you by naming its interpreter or shell differently: `python3.13 tools/apply.py --commit` instead of `python3 …`, a program text handed to `pypy3` or `node22`, a guarded script under `bash5` or `tcsh`. Since 1.0.0 a held program that is itself a script also ran unasked when handed to its interpreter by its file (`node /opt/homebrew/bin/vercel deploy --prod`), and since 1.2.0 so did `bash bin/zulu upgrade` and `sh bin/zulu rollback`. Found in our own review. Upgrading is all you need to do: nothing to reconfigure, and your policy file is not touched.

### Fixed
- **Guardrails: an interpreter or a shell named with its version is read as one.** The gate knew interpreters and shells by their exact names (`python3`, `node`, `bash` …). Under a versioned or packaged name (`python3.13`, `python3.13t`, `python3-intel64`, `pythonw`, `pypy3`, `ipython3`, `node22`, `nodejs`, `ruby3.3`, `perl5.36`, `php8.3`, `bash5`, `bash-5.2`, `zsh-5.9`, `ksh93`) a script run with its write flag passed, a program text handed over by heredoc or here-string was not read for a held action, a guarded script run by such a shell passed, and a call by absolute path was bound to the interpreter's file instead of the script, so an edit of the script after your approval was not noticed. Such a name is now read as the plain one wherever the gate asks what a program is, and so are the shells `csh` and `tcsh` (they ship with macOS), `ash`, `mksh` and `rbash`. With `renamedBins` at `enforce` such a name is still also read as an unknown program, as before, so a few forms are held under it where the plain name is clear. Nothing that was held before is freed.
- **Guardrails: a held program that is itself a script, run through its interpreter by its file.** `vercel` and `shopify` are Node scripts and `bin/zulu` is a shell script. When an interpreter or a shell is handed a script whose name is a program a rule names, the call is now also read as that program (`bash [flags] <path>/zulu upgrade` as `zulu upgrade`, `node <path>/vercel deploy --prod` as `vercel deploy --prod`), a pipe into the shell included (`cat bin/zulu | bash -s -- upgrade`). A shell's syntax check of such a file (`bash -n bin/zulu upgrade`) is held too, although nothing runs: every way of telling it from a real run was defeated by some spelling, so approve or decline it like the rest.

**Still not read** ([docs/GUARDRAILS.md](docs/GUARDRAILS.md) lists the gate's limits): a program in a language the gate does not parse (`lua`, `tclsh`, `awk`, `Rscript` and the like); an interpreter whose name is kept in a variable or comes from a command substitution (`PY=$(command -v python3); $PY …`); the script on a shell's input with its words before the file (`bash -s upgrade < bin/zulu`), which this release's trigger lines do not route; and the `zulu` program with its `upgrade` or `rollback` word handed to `eval`, `xargs` or `watch`, or echoed into a shell (`eval "zulu upgrade"`, `echo upgrade | xargs zulu`, `echo "zulu upgrade" | bash`).

## [1.2.3] - 2026-11-13

**Security: if you run Guardrails, upgrade.** In 1.2.2 and every earlier release, an agent could push to `main` (or another branch your policy holds) without asking you, by switching to it in the same call first: `git switch main && git push origin`. Found in our own review. Upgrading is all you need to do: nothing to reconfigure, and your policy file is not touched.

### Fixed
- **Guardrails: a push after a branch switch in the same call.** A push that goes through the current branch (no branch named, `HEAD` or `@`) was judged by the branch the folder stood on before the call. So from a feature branch, `git switch main && git push origin` (or `git checkout main && git push origin HEAD`) pushed to main unasked. Now every branch a switch earlier in the call names is judged as well as the folder's own, and the push is held when any of them is held; nothing is taken off that list, so no call that was held before passes now. A switch the gate cannot read (`-`, `--detach`, `--track`, an option it does not read to the end, a tag or a commit, a variable, `gh pr checkout`, `git branch -m`, `bisect`, a git or gh subcommand it does not know, such as an alias) is asked. A switch inside `sh -c "…"` counts too, as does a switch before a push inside one (`git switch main && bash -c "git push origin"`) and a switch or a push inside a command substitution (`out=$(git push origin)`). A bare push is also judged by the upstream's name under `push.default upstream` (asked when the call changes branch or upstream first), and asked under `push.default matching` or with a push refspec set for the remote. Feature-branch work away from main is not asked more (`git checkout -b feat && git push -u origin`). What the gate still does not read is listed in [docs/GUARDRAILS.md](docs/GUARDRAILS.md). Affects Claude Code and Codex agents alike.

### Changed
- **The scheduled triage pass gets four tools.** Its allow list (`--allowedTools`) only answers permission asks; tools that need no permission stayed available. Probed on Claude Code 2.1.321, the pass held 29 built-in tools (among them a helper agent, messages to other sessions, schedules and web reads) and every MCP server of the account. `scripts/triage.sh` now starts it with `--tools "Bash,Read,Write,Edit"`, `--strict-mcp-config` (no MCP servers) and `--disable-slash-commands` (no skills), next to the allow list, when `claude --help` lists all three; otherwise it starts as before and says so in the job's log. On a large board (many cards, agents and tasks), the two readings the procedure fetches are longer than one answer, and the pass can no longer hand them to a helper; it reads them in parts instead, which takes a few more calls (a smaller reading made for the pass is in 1.3). The docs no longer call the pass hard-bounded: Claude Code runs read-only shell commands without asking, and the pass may write inside the checkout ([docs/MISSION-CONTROL.md](docs/MISSION-CONTROL.md#scheduled-triage)).

## [1.2.2] - 2026-11-11

**Security: if you run Guardrails, upgrade.** In 1.2.1 and every earlier release, an agent's push to a repository on your public list could run without asking you. This happened in three families of cases, all found in our own review. Upgrading is all you need to do: nothing to reconfigure, and your policy file is not touched.

### Fixed
- **Guardrails: a Codex shell call was read against the session's folder.** Codex runs a shell command in a folder of its own choosing, but tells the hook only the command and the session's folder. The gate read the repository from the session's folder, so a Codex `git push origin feature` run in a repository whose remote is public read as an ordinary push when the session sat in a private one. A row could also describe a repository the call did not touch. Now a Codex call's folder counts only when the command names it and it certainly applies (`git -C /abs/path`, or `cd /abs/path &&` with nothing but `&&` in between). Every held Codex call whose folder is not named that way is refused without a row, unless it is a `gh` call that names its repository. The agent is told how to run it again so it can be read. Affects you if Codex agents run under Guardrails.
- **Guardrails: a folder change that fails or does not apply was believed.** The gate took a command's folder from any earlier `cd`, even one that could fail or not apply: after a `;`, an `|| true`, in a pipeline or background list, behind `false &&`, in an `if` that is false, or undone by `popd`. The command then ran in the real folder, and a push to a public remote could read as private. A `cd` now counts for certain only when nothing but `&&` joins it to the command. Otherwise the command is read in every folder it may run in, and it is held if any of them holds it. Also read now: `cd -- <folder>`, `chdir`, `pushd -n` (no change), a `cd` with extra words (unknown), and git told its repository with `--git-dir` or `GIT_DIR`. Affects Claude Code and Codex agents alike.
- **Guardrails: the remote of a push told another way.** The push rule read the remote's fetch address, by name. A push could go to a public repository and read as private in several ways. The repository's push address was public; the remote had a second push address; with no remote named, git used another remote than `origin`; or the call gave the remote another address (`-c remote.origin.url=…`, `GIT_CONFIG_*`, a rewrite rule, `git remote add up <public> && git push up …`). Now every push address of the remote git really uses is read. A literal address given in the call is used, and any other change to a remote in the same call is asked. So is a variable or a substitution as the repository. Affects Claude Code and Codex agents alike.

## [1.2.1] - 2026-11-11

**Security: if you run Guardrails, upgrade.** Two ways of starting a gated script got past the gate in 1.0.0, 1.0.1 and 1.2.0: an agent could run it without your approval. Our own review found both. Upgrading is all you need to do: nothing to reconfigure, and your policy file is not touched.

### Fixed
- **One-click upgrade from 1.2.0 would have rolled back.** Found in our own upgrade rehearsal, before any release existed to upgrade to. After the tests, the upgrade runs `node scripts/publish.mjs --check`, and in a public checkout that check counted the files published only in the public edition (`README.md`, `docs/…`) as unclassified. So the upgrade from 1.2.0 would have failed at that last check and rolled back to 1.2.0, whatever release it moved to. In a public checkout the check now reads those files as what they are; a file listed twice still fails it. The upgrade runs the check of the release it moves to, and 1.2.1 is the first release it can move to, so the one-click upgrade works with this release.
- **Guardrails: a gated script behind an interpreter flag.** For `node`, `bash` and the other interpreters and shells, the gate took the first word that looks like a script to be the script, and the value of a flag is such a word. So `node --import ./pre.mjs scripts/upgrade.mjs --to v9`, `node -r …`, `--require`, `--loader`, `--env-file`, `bash --rcfile ./rc.sh install.sh upgrade` and the same forms in front of the ledger's decision commands were not held, though the plain forms are. A rule that names a script (`scriptIn`) is now tried on every script-looking word of the call, and the flags that take a value are known, so the dry-run bookkeeping follows the right file. The `=` form (`--import=./pre.mjs`) was always held. Rules on a program (`gh`, `git`, …) and rules on a flag (`--commit`, `--apply`) were not affected.
- **Guardrails: a script handed to the interpreter on its input.** `node < scripts/upgrade.mjs`, `cat install.sh | bash -s upgrade`, `sh -s -- gate 5 g1 approve < scripts/task.sh` and `node - --commit < scripts/rename.mjs` were not held: the rules that name a script did not see the file, and for the redirect form the rules on a flag did not either. An input redirect, a pipe from `cat` and a here-string that is one file's content are now read as the plain run of that file, when the call names no script or program of its own. Readers of the same files (`wc -l < install.sh`, `cat task.sh | grep gate`) stay free. What the gate still does not read as a run of a named script is listed in [docs/GUARDRAILS.md](docs/GUARDRAILS.md#writing-rules).
- **Tests: demo boards started together no longer kill each other.** A demo board empties and re-seeds its ledger folder (`data/demo-tasks`) at startup. Several tests start a real demo board from the checkout and the test runner starts test files side by side, so two boards could remove each other's files mid-write; the loser died at once and its test waited 15 seconds for a board that was already gone ("demo board answered"). This failed about one full run in four on a busy machine, and `./install.sh verify` and the one-click upgrade run the suite on your machine. A demo board now takes its ledger folder from `MC_DEMO_TASKS` when set (default unchanged), every test gives its board a folder of its own, and a test fails when a new one forgets. A folder named that way must be empty, or one a demo board seeded before (it then carries a marker file); anything else is refused and left as it was, and your real ledger folder (`data/tasks`) is refused whatever it holds.
- **Tests: two more timing tests judge the third-fastest run.** Like the hook's fast-path test in 1.2.0, two other tests timed the hook over 60 runs and required the median under their ceiling, which a busy machine moves. They now judge the third-fastest run, and a test names any test that judges a median. The Guardrails-only board test now waits for a whole poll before it reads which stages ran.

### Security
- **Guardrails: text in a call could turn the gate's answer into silence.** After its Node step had answered, the hook's shell script decided whether a call had already run by looking for the after-call event's name anywhere in the raw hook input. That input holds the call's own words, so a held call whose command, comment or tool input contained that name ended with no output, and no output lets the call run. With the board up, the gate was filed and the call ran anyway. The Node step, which reads the input properly, now says by itself when there is nothing to say; the shell reads the event only when the Node step could not answer, and only from the input's own key, in a form a string value cannot produce and only when that key occurs once. `gate-replay.mjs --mentions <word> --list` lists past checks that name a word (time, agent, event, answer; never the call's text), so you can look for past calls of this kind.
- **Guardrails: the gate hook no longer believes the session's environment, and answers before its time limit.** Two things were seen on Claude Code 2.1.321, in scratch folders: a settings file's `env` block reaches every hook process of the sessions in that folder, and a hook that answers after its registered time limit lets the call run. On a copy of the hook script as it was, one settings file in a repo was enough to make a gated call pass (its own `cat` first on `PATH`, a preload in `NODE_OPTIONS`, or `MESH_BOARD` pointing at another listener), with no change to any gate file.
  - The script now puts the system folders first on `PATH` and clears the variables that load other code before it runs anything.
  - The board's address comes from the checkout's own `data/local.env`, else the default port. An environment that names another board gets no request sent anywhere: gated calls are denied and the reason names both addresses. **If you export `MESH_BOARD` or `MC_PORT` in your shell and it does not name the board the hook belongs to, unset it.**
  - The Node step runs under the script's own 12-second deadline, below the registered 15, and the script answers "deny" itself when it passes. `GATE_TIMEOUT_MS` can only shorten the 8-second wait for the board.
  - Speed is unchanged: about 14 ms for a call that hits no trigger.
- **Guardrails: hash-chained receipts.** Every change to a gate appends one line to `receipts.jsonl` in the Guardrails state folder, each carrying the hash of the line before. `task.sh audit N --verify` recomputes the chain and compares it with the task's gates; the `guardrails` card does the same over every task at start and every six hours and goes red on a difference. An approved call now runs only when the chain holds the approval the running board recorded: an approval written into the files by hand is refused, the gate is marked `disputed` and the card goes red. A line that cannot be written never fails a gate event (the card goes amber and the line is written with the next one). Switch: `SETTINGS.receiptChain` (`on` by default; `observe`, `off`). See [docs/GUARDRAILS.md](docs/GUARDRAILS.md), The receipt chain.
- **Guardrails: a guarded file is held however the call reaches it.** The hook's fast path looked for a guarded file as its folder and name side by side, so `cd data && cat <file>`, `data/./<file>`, `data//<file>` or a call made from inside the folder never reached the rule. The fast path now looks for the bare file name, and for a guarded folder also in the folder the call is made from; `/./` and a doubled slash are dropped first. On macOS `/System/Volumes/Data/<path>` is read as `<path>`. A bare name only sends the call to the rules: a script in another repo that names `settings.json` or `webhooks.json` is not held for it. An interpreter's program run from inside a guarded folder is held. A glob or a variable in a path is still not read.
- **Guardrails fix: a check in `observe` no longer changes the hook's answer.** A fast-path line that only an observing check adds made an interpreter's program or an assignment naming one of that check's paths (a shell start file, `.git/hooks/`, a hook-session file) opaque, so the call was held although the check was only observing. Such a line now routes the call and gives the "would hold" reading, and decides nothing until the check is set to `enforce`. On the shipped default this affected `selfProtect` and `renamedBins`.
- **Guardrails: another letter case is the same file, script and program.** On a disk that ignores case (the default on macOS and Windows) the rules matched names exactly, so the rules file or the gate's state could be reached under another spelling (`Overlay/POLICY.JSON`), a guarded script could be run as `TASK.SH`, and a gated program as `GH`. Paths, script names and program names are now compared without case there. This is a fix, not a switch.
- **Backups can no longer carry the phone relay's credentials.** `zulu backup` used to walk all of `data/` and leave out a fixed list of names, so the relay folder (its user database and the phone's token file) went into every manual archive. Credentials are now left out by three rules: a folder holding a `.nobackup` file is skipped whole in every kind of backup, `--with-secrets` included (`data/relay/` gets the file from the backup itself and from the upgrade); a file only its owner can read is left out unless it is in one of the board's state folders; a small file whose text looks like a key is left out. The backup prints what it left out and why. A restore refuses to write into a marked folder, puts each file's mode back, and brings credentials back only with `--with-secrets`. If you copied an earlier full backup off your machine and use the relay, treat the phone's token as exposed and make a new one. Note: files that agents saved owner-only under `data/handoffs/` are now left out of a backup unless you pass `--with-secrets`.
- **Guardrails: a quoted here-string to a shell is read.** `bash <<< "gh pr merge 5"` was read as an argument of `bash` and passed. The word after `<<<` or `>` is now that operator's target whether it is quoted or not. This is a fix, not a switch.
- **Guardrails: a gated command behind a shell keyword is held.** A command written after `then`, `do`, `else`, `elif`, `if`, `while`, `until`, `coproc` or `!` (`if …; then gh pr merge 5; fi`) was read as the keyword's arguments and passed. The program is now the word after the keyword, so the command is judged like any other. This is a fix, not a switch.
- **An answer you gave in a pane no longer approves by itself.** When an agent records "the owner said yes" (`task.sh approved-in-pane`, or Mission Control's `task.sh gate-approved`), the record is now a proposal. Your row on the board quotes it and names who typed it, and you click **CONFIRM**, **DECLINE** or **NOT WHAT I SAID**.
  - Until you confirm: the gate stays pending and no grant is minted, no program go starts, and a plan-first plan is not approved.
  - Before, the record was the approval. It rested on a name the agent declared for itself, so an agent could approve its own gate by claiming to be Mission Control, and a task's owner could grant its own program go.
  - A recorded decline still takes effect at once.
  - `SETTINGS.paneAnswers: 'direct'` restores the old behaviour. The default, also when the key is absent from your config, is `'confirm'`, so an upgrade changes this for you: a pane answer now needs one click on the board.
- **The decision door.** The board now looks at the process that holds the connection before it takes an owner decision (`SETTINGS.callerEvidence.tripwire`).
  - `'agent'`: an approve, decline, snooze, card action or upgrade that an agent session is behind is refused, with the decision token or without it, and Mission Control is told which agent. Before, an agent that fetched the token from the board page could post an approval.
  - `'browser'`: also, a decision made on this machine must come from a browser or web view. Under `'agent'` this is only logged (`[door] would refuse`), so you can read what it would stop before you turn it up.
  - A decision typed as a `!` line inside an agent's pane is refused under both: the board cannot tell it from the agent. Decide on the board page.
  - A request from another device and a request the board could not look up are never refused by the door. Each decision that passes with no evidence of its sender is logged, put on the ticker and counted.
  - A sender that writes its request and leaves (it exits, or resets the connection) is not a failed lookup. It is logged under `'agent'` and refused under `'browser'`.
- **The board checks agent names against the calling process (observe).** `SETTINGS.callerEvidence.mode: 'observe'` records, next to the name an agent declared, the agent the board worked out from the process ancestry and cmux's session map. A mismatch between two agents reaches the ticker as `[caller mismatch]`. Nothing is refused on names in this release. The lookup runs before the answer goes out, so a ledger or mesh write takes about 160 ms longer while this is on. Needs `lsof`.
- **Agent names can be enforced.** `SETTINGS.callerEvidence.mode: 'on'` (not the shipped setting, which stays `'observe'`) makes a declared name count only when the calling process backs it.
  - A name it does not back keeps its words and loses its standing: a message, a comment or a new task still goes out, marked `UNVERIFIED` and recorded under the board's name with the reason. Claim, start, close, reassign, a gate focus and Mission Control's steps are refused.
  - The gate hook's identity comes from the session behind the hook's call. A child session started with an observed agent's workspace id is now judged as the session that started it. A lookup that fails, or a cmux session the board cannot name, is enforced whatever it declared.
  - Headless runs are named by their launchd job (`callerEvidence.jobs`) or by the workspace the board opened for a card dispatch. The `MESH_GATE_IDENTITY` variable is ignored under `'on'`; it still works in `'observe'`.
  - The owner's name still needs the decision token, and under `'on'` is not accepted from a process an agent session is behind.
  - Read a week of `[caller mismatch]` lines in `'observe'` before you turn this on. A scheduled script that uses an agent's name needs an entry in `callerEvidence.jobs`.
- **An approval typed in a terminal becomes a row you confirm** (`callerEvidence.tripwire: 'browser'`). `task.sh gate N gK approve` from your own terminal no longer decides on a board that takes decisions from its page only. It prints `NOT approved yet`, the gate stays pending with nothing minted, and the gate's row says an approval was typed in a terminal and that the board cannot tell who typed it. One click confirms it; **I DID NOT TYPE THIS** throws it out and tells Mission Control. A typed decline is refused: decline on the board page. Under `'agent'` nothing changes, and the server log says what `'browser'` would do with each typed approval.
- **Board down: the hook reads its session from the agent process above it.** A child session started with an observed agent's workspace id in its environment is now enforced when the board is unreachable.
- **Receipts: `phone` means another device.** A decision this machine made through its own tailnet address is recorded as local.
- **Card actions need your decision token.** The buttons on a card (kickstart, restart, start, dispatch a session, ask the master) now go through the same check as a gate decision: the board page's token, and no agent or intake identity. Before, any local caller could post them.
- **Every write is checked for where it came from.** A POST, PATCH, PUT or DELETE is refused (403) when its `Origin` is another site, when the browser marks it cross-site, or when it was addressed to a host name the board does not answer to. Requests with no `Origin` (curl, the hook, scripts) pass as before. A body must be declared as `content-type: application/json` (415 otherwise). If you reach the board by a name of your own, list it in `SETTINGS.allowedHosts`.
- **The owner's name and `board` are reserved as senders.** A mesh message or a task wake under the owner's name is the owner's only with the decision token (the board page, or `--signed` from your own shell; an agent that runs the ledger or mesh CLI with that flag is held as class `self`). `board` is the board's only from its own process. A message that claims either name without proof is still delivered, marked `UNVERIFIED sender`, and is not written to the ledger under that name.
- **Wakes for intake tasks carry the id and the source only.** When a task came from the team chat, from GitHub or from a channel name, the text typed into an agent's pane no longer contains the title, the body or a comment. The agent reads the task from the ledger.
- **Guardrails: a default mode, with readings first.** The policy takes `defaultMode` (`observe`, the shipped default and today's behaviour, or `enforce`) and `observeFor`. With `enforce`, every session is held, registered or not, except the names in `observeFor`. Headless runs the board starts (triage, a dispatched fix session) now resolve as `headless:<role>`. While the default is `observe`, every call the other setting would have held is logged as "would enforce". See [docs/GUARDRAILS.md](docs/GUARDRAILS.md).

### Fixed
- **`ZULU_NO_LAUNCHD=1` now covers the full installer.** Only `--guardrails` and `zulu setup` honored it, so a test install under a temp `HOME` still loaded real LaunchAgents. `scripts/bootstrap.sh`, a backup restore and the job installers now skip `launchctl`; `zulu upgrade` and `zulu rollback` refuse (`--check` still works).
- **cmux is looked up, not assumed.** The shipped registry named a fixed Homebrew path for cmux. It is now found on `PATH` (a full path in `SETTINGS.cmuxBin` still pins one). On a Mac with no cmux the `cmux:bridge` card says so in amber; before, it could read "socket auth OK". With no cmux the board skips the session heal and sends desktop notices through macOS.
- **Ledger: concurrent first reads.** Two requests arriving while the board read the ledger for the first time could see a half-filled list, and a task created in that moment could take an id that was already on disk and overwrite that task's file. The first read is now shared by every caller.
- **Docs: twelve places where the docs disagreed with each other or with the code.** One macOS version (26, the version each release is tested on; "14 or later" was never tested). What the one-line installer really installs and loads: the Codex CLI, Graphify and Obsidian by default, the brain step without a question, and a scheduled triage job that costs money, with how to leave each out. Where credentials live (the file you fill, plus three the board generates and the relay's folder). The one file outside its checkout that the board writes (cmux's config, to restore the socket password). What the decision token covers, and that the board page carries it. That an approval is a click on the board, also from the phone over your tailnet, and that a push only rings. That an agent the board cannot reach is not woken after an approval and runs the command again. One-click upgrade is described as part of this release, not as present "since 1.1". An older backup is migrated forward, not refused. The roadmap names the latest release.
- **Guardrails: a program go is stricter about which repo a landing reaches.** A landing now runs by itself only when the `gh` call is the whole command (a leading `cd <folder> &&` and a plain `GH_REPO=<owner/name>` prefix are fine); with anything else in the same text it asks you, and the agent is told to run it as its own command. The repo flag is read inside a group of short flags (`-sR <repo>`). With no repo named, every remote of the checkout and every `gh-resolved` key must point at the origin's repo, because that is where `gh` looks. These only ever make it ask more.
- **Guardrails: a program go judged the wrong repo for a landing named by URL or `GH_REPO`.** `gh pr merge https://github.com/<owner>/<name>/pull/N` and `GH_REPO=<owner>/<name> gh pr merge N` were checked against the checkout's own repo, so a go for work in a private repo also auto-ran a landing into a public, deploy-on-push or unknown repo named that way. The board now collects every repo the command names (the repo flag, a PR URL, each `GH_REPO` assignment) and uses it only when they agree on one github.com repo; two different names, an unreadable name, another host or `GH_HOST` ask you. Without a program go these commands were always held.
- **"Not approved yet" always reaches the agent.** When a pane answer was recorded for a gate, the notice telling the waiting agent not to retry could be replaced in its queue by any later message about the same task. It is now a kind the queue never replaces, and it is dropped only once you have decided. The notice sent when you reject a record is the same kind.
- **"Not what I said" puts a task back where it was.** If the task had moved on before the pane answer was recorded, rejecting the record left it waiting on you with plain approve and decline buttons. It now returns to the status it had.
- **The agent feed no longer reads the whole workstream file.** `/api/feed` and the log view read the last 256 KB, cached by size and modified time. On a file of a few hundred MB the old read ran on every open tab's refresh.
- **Alerts no longer wait behind mesh work.** The alert pass and the dead-man heartbeat run straight after the snapshot. Each poll stage runs in its own try, so one failing stage cannot skip the others.
- **A stray promise rejection no longer stops the board.** It is logged with a timestamp and the board stays up. An uncaught exception is logged, then the process exits for the supervisor to restart.
- **The morning briefing survives a restart.** Its day is kept in `data/digest-state.json`. A restart after the briefing hour neither skips nor repeats it, and a failed send is retried twice.
- **A message queued while the outbox is being delivered is no longer lost.** Queueing, delivery and dropping go through one writer per outbox file.
- **Dock order.** The `?dock=1` column now reads header, then NEEDS ATTENTION with your one-click decisions above the amber and red cards, then WAITING ON you with the blocked tasks and snoozed items folded. Blocked tasks no longer fill the top of the column. The full board keeps its strip.
- **Gate buttons no longer sit below the command.** A gate row now shows what it is, why it was held and who asked, then ✓ RUN ONCE / ✕ DECLINE, then the command. A command over 6 lines or 480 characters starts folded with a "show full command" toggle; unfolded, it is the exact, uncut text. In a narrow column, a long task title no longer pushes DECLINE off the side.
- **Guardrails: `gh` flags placed before the subcommand.** `gh --subject x pr merge 5` is a real merge, but the flag's value read as the subcommand, so it wasn't gated. It is now.
- **Guardrails: harmless chained commands were held.** A read followed by an unrelated command on one line, such as `gh pr view 5 && git merge --abort`, could look like a gated `gh pr merge` and wait for your approval. The gate now judges each command, and only a real match holds.
- **Guardrails: policy files in a git worktree.** The gate protected `policy.json` only in the live checkout, so an agent could edit the copy in a worktree without asking. Those copies now need your approval too.
- **Guardrails: the word "gate" in a message no longer holds the command.**
  - **What went wrong:** the fast-path trigger for `task.sh gate` (and `mesh-cli.mjs task`) let any text sit between the script name and the word. A `task.sh comment` whose text said "merge gate" set it off. So did a later command on the same line, such as an agent message. The parser judges each command separately, so it couldn't account for the hit and held the call as unreadable, waiting on you.
  - **Fix:** a script rule's argument is its subcommand, and now has to follow the script name directly.
  - **Unchanged:** a real `task.sh gate N gK approve` from an agent still gates.
- **Guardrails: Mission Control's focus.** `task.sh focus N` already let Mission Control focus a task another agent owns, but the hook only honored a focus on the caller's own tasks, so Mission Control's gates were refused with "live tasks and no focus". Its focus now counts on any live task.
- **Guardrails: a pending gate could fall off WAITING ON YOU.**
  - **What went wrong:** the waiting list only read tasks whose status was "needs approval". A task that was blocked and then unblocked went back to "in progress" while its gate was still pending. The gate stayed off the strip, `?dock=1`, the sidebar ATTENTION list and the cmux pill, and the phone relay was the only place that still showed it.
  - **Ledger fix:** a task with a pending gate stays in "needs approval" through any status change (unblock, start, claim, assign). It leaves only when the gate is decided.
  - **Display fix:** the summary and the pill also treat any live task with a pending gate as waiting on you. This covers tasks saved before the fix.
- **Brain: "graph behind" from data-only commits.** A commit that touches only data or binary files (spreadsheets, CSV/TSV, images, PDF, zip, `.ics`, `.plist`, lock files, any letter case) no longer counts as code for the graph-behind check or for the close gate's `graphify_updated`. graphify never extracts these, so the graph never moved and the repo read as behind forever.
- **A task's original request can no longer scroll away.** New tasks keep the request in its own field. On older tasks the comment cap (200) now keeps the first comment when it is the request. No existing task file is rewritten.
- **Worktree cleanup after a squash.** A branch that was sent to the remote without tracking and then squashed and deleted left no proof, so `worktree-clean` refused. It now looks the PR up by branch name and accepts a landed PR whose head is exactly the local head.

## [1.0.0] - 2026-10-31

The first stable release. Its headline is **Guardrails**: an agent's irreversible actions wait for your approval, run once, and leave a receipt. The release also adds a written security model, backup and restore, and a context autopilot that compacts agents before they run out of room.

**Upgrading from a beta:**
1. Follow [docs/INSTALL.md §7b](docs/INSTALL.md#7b-upgrading): take a backup, `git pull`, `./install.sh`, restart the board.
2. `./install.sh` adds the new example files (such as `overlay/policy.json`) and never overwrites yours.
3. To turn on the new settings in an existing `overlay/config/jobs.mjs`, copy them from `examples/config/jobs.mjs`: `CONTEXT.warnPct/compactPct/forcePct` and `SETTINGS.contextAutopilot`.
4. Guardrails need their hook installed once: `scripts/guardrails-install.sh --apply [--codex]`. Then restart the agent sessions.
5. Tested versions are in [docs/VERSIONS.md](docs/VERSIONS.md). One-click upgrades come in 1.1.

### Added
- **Context autopilot.** The board compacts your agents before their context runs out, instead of the CLI's own auto-compact cutting in mid-thought.
  - At 70% it asks the agent to save its state file. At 80%, once the save has landed, it types `/compact` at the agent's next idle moment. At 90% it compacts even without a save and tells Mission Control.
  - After the compaction it tells the agent to re-read its state file and carry on with its task.
  - It never types into a busy pane, a dialog or a half-typed draft. One try per 10 minutes, and after 3 failed tries it stops and says so.
  - `SETTINGS.contextAutopilot` (`mode: 'off' | 'observe' | 'on'`, `only`, `exclude`), off in the examples. The gauge colours now follow the thresholds (amber 70, red 80).
- **Gate receipts say where you decided:** board, phone, Dock, the WAITING ON YOU strip, the CLI or a recorded pane answer (`surface` / `surfaces` on each gate; also shown in `task.sh audit`).
- **`zulu backup` / `zulu restore`.** Backup writes your ledger, state and config (`data/` + `overlay/`) to one tarball with a manifest of hashes.
  - It's lean by default: from `data/handoffs/` only text files up to 1 MB. `--full` keeps media and big exports too.
  - Every backup prints its size and what it left out.
  - Left out: the decision token, gate grants and earlier backups always; secrets unless you add `--with-secrets`.
  - Restore shows what would change and checks every hash. It refuses a backup from a newer schema; migrating an older one forward arrives with the 1.1 upgrade migrations (1.0 has one schema). `--apply` takes a safety backup first. Secrets come back only with `--with-secrets` on the restore too.
- **[docs/SECURITY-MODEL.md](docs/SECURITY-MODEL.md):** who is trusted, what the Guardrails gate stops and what it doesn't, the decision token, network exposure and secrets. The README gains a Guardrails section.
- **Guardrails: owner gates for irreversible agent actions** ([docs/GUARDRAILS.md](docs/GUARDRAILS.md)). These commands no longer run when an agent tries them: merges, pushes to protected branches or public remotes, deploys, secret changes, a guarded script's `--commit`/`--apply` run (dry run required first), outbound sends, MCP store writes, deletes outside the working tree, schedule changes and edits to the gate itself. Each waits for the owner on the ledger. The owner approves the exact call on the board or a phone: a shell command's text, or a tool's whole input such as an MCP mutation's arguments or an edit's old and new text. It runs once on a single-use grant that never leaves the board. Every attempt, decision and run is a receipt on the task (`gates[]`, `task.sh audit`), and a task can't close with a gate unresolved.
  - Claude Code and Codex, through a PreToolUse hook (`scripts/guardrails-install.sh`).
  - The policy lives in `policy.json`, rendered into `POLICY.md`, with observe mode and per-agent pilot enforcement.
  - Fail closed: if the board is down, gated calls are denied, and calls that aren't gated pass in milliseconds.
  - Demo mode shows a gate.
  - **Program go:** one owner approval of kind `program` on a task lets that task's *standing* classes run without a per-action tap, each with a receipt. By default those are merges into confirmed-private repos and local service loads. Revocable from the board or `task.sh revoke-go`; it ends at task close.
  - **Decide anywhere:**
    - a pinned *WAITING ON YOU* strip at the top of the board, the Dock view and the phone, with a "(N)" count in the tab title;
    - the count in the phosphor sidebar;
    - `task.sh gate N gK approve|decline` from the owner's own terminal (gated if an agent runs it).
  - **Judged where it runs:** each command is judged in the folder it really runs in (`cd …`, `git -C`). Outside any git repo, `rm -r` gates.
  - **Fewer false alarms:** `--help`/`--version`, and an agent cleaning its own scratch folder, aren't gated.
  - **Scripts that write without a flag** can be listed in `@guardedScripts`, which gates them on every run.
  - **Approvals reach the agent:**
    - the notice is delivered inside a busy session and can't be replaced by a later message about the same task;
    - the agent's sidebar shows `⛨ gK APPROVED — run it` until it runs;
    - approvals last 120 minutes.
    
    One that expires unused is never re-armed: the next attempt asks again and says it was approved before.

  down. New media in `docs/media/` (`cmux-demo.gif`, `two-part-console.png`, `cmux-attention.png`).
- GitHub repo stats on the board (`SETTINGS.repoStats`): stars, forks, watchers, clones and views as
  cards and a digest section, with history kept beyond GitHub's 14-day window (`data/repo-stats.json`).

### Fixed
- Workspace listings span every cmux window (`src/cmux-windows.mjs`); a board running outside cmux no
  longer sees only the front window, which could have marked the whole fleet closed. A failed listing is
  treated as no listing, never as closures. Demo workspaces never join the mesh.
- `agent-close.sh` passes `--force` (cmux 0.65 requires it for a workspace with a live process).

## [0.1.0-beta.1] - 2026-10-09

First public release.

### Added

**One-command install and guided setup**
- `get.sh` one-liner (uses `gh` when available), and `scripts/prereqs.sh`, which installs
  only the missing toolchain after one confirmation.
- `zulu setup`, a resumable wizard with live checks: GitHub, engines, owner and policy, a scan of
  this Mac for what to watch, alerts, an Obsidian vault from the template, Graphify and memory,
  macOS permissions, residents, verify. The board shows a setup card until it is done.
- Claude Code or Codex per role (Mission Control, workers, residents, triage): `scripts/engine.mjs`.
- `zulu doctor`: a redacted diagnostic file for bug reports (never uploaded).
- `overlay/config/local.json`: setup answers merged into the registry; `example: true`
  placeholders drop out once real items are chosen.

**Ops Board**
- Zero-dependency Node ≥ 22 server on port 3210, with a 60s poll, SSE push to
  the browser, and `/api/status` for scripts and agents.
- Watches launchd jobs (schedule, logs and selfheal markers auto-discovered
  from the plist; `quietOk` watchdogs judged by exit code), docker
  containers, HTTP endpoints, a disk gauge, a memory/swap gauge, bare
  processes, and user crontab lines (with a zero-dependency cron parser and a
  drift check against `crontab -l`).
- Agent session tiles for Claude Code and Codex sessions in cmux: running,
  idle or needs input, the last message, and a context-window gauge (amber
  ≥ 60%, red ≥ 80%, estimated after a compaction).
- Phosphor UI: rack-module cards, a 24h ops timeline, an event ticker, a
  `?tv` kiosk mode, a `?dock=1` compact view, a `/` command palette, CVD-safe
  status chips (glyph plus label), and `prefers-reduced-motion` support.
- Opt-in actions: KICKSTART (launchd), RESTART (docker), START (processes),
  DISPATCH CLAUDE (a diagnostic session in a new cmux workspace), ASK MASTER.
- Source guard: localhost and Tailscale CGNAT only; the LAN gets 403.

**Alerting and self-protection**
- Escalation ladder: cmux notification → email after 30 red minutes → SMS
  webhook for the critical set → 08:00 daily digest. Alerts are deduped and
  re-sent every 6h while a card stays red.
- Dead-man's switch: a heartbeat row is updated every poll, and an example
  GitHub Actions workflow emails when it goes silent.
- Disk auto-remediation mechanism with a 24h cooldown (ships with an empty
  lever list).
- cmux socket-password self-heal and a retry for failed session restores
  after a reboot.

**Agent workforce**
- Mission Control: a master agent in a pinned cmux workspace, with a contract
  template, `POLICY.md` approval authority, residents with
  `RESIDENT-STATE.md` continuity, ephemeral workers with a report-back
  protocol, and scheduled headless triage bounded by `--allowedTools`.
- Agent Mesh: a directory keyed by cmux workspace (addresses follow renames),
  a task ledger with a checklist-gated close and refusal of secret-like text,
  owner approvals on the board's WORK panel behind a decision token, and
  delivery only into READY panes with a 24h outbox.
- Optional cmux chrome: workspace colors per domain, descriptions, task pills,
  and context progress. Values you set by hand always win.
- cmux Dock and a phosphor custom sidebar (installer with backup and revert).

**Setup and publishing**
- `install.sh` with `--demo` mode (synthetic data; no launchd or cmux).
- `install.sh init | --brain | mission-control | star | demo-stop`, and a `bin/zulu`
  wrapper.
- Demo mode (`MC_DEMO=1`): a scripted incident loop, plus agents and a ledger, for
  trying the board and recording it. It keeps its own ledger, ticker and toast
  state, so it never touches a real board's `data/`.
- A configurable ledger close checklist (`SETTINGS.ledger.checklist`; the default is
  docs + report).
- Consent-first star surface: the installer asks once (default No, your own `gh`
  login), and the board shows one toast (Star opens the repo page; Never ask again).
  A "share your setup" button renders a redacted PNG locally for download.
- Overlay config (`overlay/` → core → `examples/`) and secrets in
  `data/secrets.env` only.
- `scripts/bootstrap.sh check | install | verify`, and LaunchAgent and cmux
  templates rendered without hard-coded paths.
- Publish manifest (checked locally with `scripts/publish.mjs --check`), and the scrub gate
  and gitleaks in CI.
