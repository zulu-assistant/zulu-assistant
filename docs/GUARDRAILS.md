# Guardrails: owner gates for irreversible agent actions

**What it is.** When an agent tries something irreversible (merging a pull request, pushing to `main`, deploying, a script's `--commit` run, sending a message, a store write, a delete outside its working tree), the command **does not run**. It waits for the owner on the ledger. One approval, from the board or a phone, lets **that exact command** run **once**. Every step (attempt, decision, run) leaves a receipt on the task.

**What it is not.** It is a hard stop for the agent's own tool calls (Bash, MCP tools, edits of the gate's files), in Claude Code and in Codex. It is **not** a sandbox against a hostile program running as your user. A script the agent writes and then runs can call `gh` inside it, and the hook only sees `bash deploy.sh`. One case fails open: if `/bin/sh` itself cannot start, the hook can't answer and the tool call runs; the `guardrails` card reports a missing hook. The realistic failures it stops:
- a model misreading scope;
- a relayed or ambiguous "go";
- a dry run chained into `--commit`;
- a confident wrong merge.

## How a gate goes
1. An agent runs a gated command. The **PreToolUse hook** (`scripts/gate-hook.sh`) stops it before it runs.
2. The hook asks the board (`POST /api/gates/check`). The board classifies the call with **its** policy and files a gate on the agent's current task. The task goes to *needs approval*, the owner gets a desktop notice, and the agent is told: `GATE: … Waiting on the owner, task #N (gate gK). You'll be woken when they decide; do not retry it or work around it.`
3. The owner opens the WORK panel (the phone works over your tailnet). Each gate row shows the **folder, agent and age**, then **✓ RUN ONCE / ✕ DECLINE**, then the **full command**, wrapped. A command over 6 lines or 480 characters starts folded: "show full command" opens all of it. A non-shell call shows the tool and its whole input: an MCP call's arguments, an edit's old and new text. The task keeps up to 20,000 characters, and a longer input is cut and says so. Like every board decision, it takes two clicks.
4. **Approve:** the board mints a **single-use grant**. The grant is bound to a hash of the exact call (folder + tool + engine + the shell command's text, or for any other tool its **whole input** as canonical JSON), the agent and an expiry (120 min by default). So a grant for one Shopify mutation can't run a different mutation, and a grant for one edit of a file can't make a different edit. It stays in `data/guardrails/grants.json` (mode 600) and is never sent anywhere: not to the agent, the page, a log or the ledger.
   - **The notice arrives for an agent the board can reach.** An agent registered in the mesh (a session in a cmux workspace) is woken (`GATE gK on #N APPROVED — run exactly: …`). That notice is delivered inside a busy session, and no later message about the same task can replace it in the queue. A session the board cannot type into (one started outside cmux, or not registered) gets **no wake**: it runs the same command again after you approve, and the grant lets it through. Until it runs, the agent's sidebar label leads with `⛨ gK APPROVED — run it`.
   - **It runs once.** The agent re-runs the command; the hook finds the grant, consumes it and lets the call through. Any change to the command is a new gate. So is running it a second time, and so is the same command from another folder or agent.
   - **Unused approvals expire.** An approval that expires before it ran is never re-armed: the next attempt asks again. That row says *↻ you approved this exact call at 13:52Z (g8); it expired before it ran*, and the agent is told so.
5. **Decline:** the agent is told not to retry. A re-attempt is counted on the gate, and the task can't close until that is waived with a reason.
6. **Receipts:** `gates[]` on `GET /api/tasks/N`, one ledger comment per step (`GATE g1 requested · merge · gh pr merge 38 … / APPROVED by <owner> (board, phone/tailnet) / released to run once 11:42:07Z (single-use grant) — the agent reports the outcome on this task`), and `task.sh audit N` (add `--json` for the raw records).
   - **"Released" is not "done".** The board lets the call through; the command then runs in the agent's own process, and the board never sees whether it succeeded. The agent reports the outcome on the task. In the stored data the status is still called `executed` (the 1.0 name, kept so existing ledgers need no migration); everything you read says *released to run once*. A rename of the stored value can come with a later upgrade migration.
   - Each decision also records where it was made: `surface` is one of `board` (the WORK panel), `phone` (over the tailnet), `dock` (the `?dock=1` view), `strip` (the pinned WAITING ON YOU strip), `cli` (`task.sh gate`) or `pane` (a decline Mission Control recorded; an approval too, only under `SETTINGS.paneAnswers: 'direct'`). `surfaces` lists every one that applies, e.g. a phone tap in the strip.
   - A pane answer that was recorded and then confirmed shows as two rows in `task.sh audit`: `pane answer recorded` (who typed it, and the words), then `approved` on the board, "confirming the pane answer recorded by …".
   - `phone` comes from the request's network address, so the page can't claim it. It means another device on your tailnet: a call this machine makes to its own tailnet address is recorded as local.
   - This is a receipt only: it never changes who may decide.

**Where the owner decides:**
- **The board.** While anything waits, a pinned **WAITING ON YOU** strip sits at the top of the board and the phone. In the Dock view (`?dock=1`) your one-click decisions lead **NEEDS ATTENTION** under the header instead, and tasks blocked on you wait in a closed section below. The strip shows pending gates and approval requests, oldest first, with the same two-click buttons. The tab title shows the count, `(2) Zulu Assistant`. The phosphor sidebar can't make network calls, so it shows the count instead: `⛨ 2 GATES · #343 …` leads that agent's progress label.
  - With `SETTINGS.attention.snooze: 'on'` the strip groups by task (one row per task, expand on click) and each row can be snoozed 15m / 1h / 4h / until 08:00 tomorrow. A snooze only hides the row and lowers the count; the gate stays pending, its grant window is unchanged and the agent is not held. Snoozing needs the board page's token and no agent identity, like a gate decision.
  - **What a waiting row tells you.** Beside the class, a row carries a chip when the call is of a kind worth a second look: `public repo` or `deploys on push` (the target repo is on your `publicRemotes` or `deployOnPush` list), `sends outside`, `store write`, `the gate itself`, `desktop control`, `unlisted tool`. The chips come from the class and your lists, never from the agent. The agent's own description of its call is shown on a separate line labelled **agent's words**: read it as a claim, not as a fact. A dry run's time links to the task's receipts when the evidence panel is on.
- **The owner's terminal:** `task.sh gate N gK approve|decline ["reason"]`, typed in a terminal of your own. It uses the board's decision token from `data/mesh-decision-token` and is recorded as `(cli)`. An *agent* running the same command is gated (class `self`), so it can't approve its own gate.
  - **Not as a `!` line in an agent's pane.** The gate hook does not hold a line you type yourself, but with the decision door on (below) the board refuses a decision that comes out of an agent's session: it cannot tell your `!` line from the agent typing the same thing. Decide on the board page.
  - **With the door at `'browser'`, a typed approval is a row you confirm.** The command prints `NOT approved yet`. The gate stays pending and no grant is minted. The gate's row on the board says an approval was typed in a terminal and that the board cannot tell who typed it. Click **✓ CONFIRM · RUN ONCE** and it is approved, as any board approval. Click **⚑ I DID NOT TYPE THIS** and the record is thrown out, kept on the receipt as rejected, and Mission Control is told. A typed decline is not kept: decline on the board page.

**The decision door** (`SETTINGS.callerEvidence.tripwire`). The board does not take a decision request on trust. It looks at the process that holds the connection:
- **`'agent'`:** an approve, decline, snooze, card action or upgrade that an agent session is behind is refused with a 403, logged, put on the ticker in red, and reported to Mission Control by name. This is what catches an agent that fetched the token and posted an approval.
- **`'browser'`:** in addition, a decision made on this machine must come from a browser or a web view (the system WebKit process, or an app on `callerEvidence.browsers`). A plain program is refused. One request is kept instead of refused: an approval of a gate typed in a terminal becomes a row you confirm (above). It decides nothing by itself. Under `'agent'` the board only logs what this would do (`[door] would refuse`, or `[door] would keep as a row to confirm` for a typed approval, in the server log); read those lines before turning it up.
- **What it never refuses:** a request from another device (your phone), and a request it could not look up. The second is deliberate: a slow `lsof` must not lock you out of your own board.
  - **A pass without evidence is never silent.** Each decision that goes through with no evidence of its sender leaves a `[door] passed WITHOUT evidence` line in the server log and a red ticker line, and is counted (`passedNoEvidence`, `lastNoEvidence`).
- **A sender that has left is not a failed lookup.** A program can write a decision request and exit, or reset the connection, before the board looks at it. The board tells this apart from a lookup that could not run: its own end of the connection is still there and nobody holds the other. Such a request is logged under `'agent'` (`[door] would refuse (its sender has left)`) and refused under `'browser'`. The board page and a command line both wait for their answer, so your own decision is never in this state.
- **What it is not:** proof that a request is yours. A background command has no agent session behind it (its shell is gone by the time anyone looks), and an agent can drive a real browser. The first is why `'browser'` exists; the second is what holding desktop-driving tools is for. Neither replaces an owner-held key.
- Every `[door]` line names the program, the kind of caller the board saw and why it called it that, so the lines can be sorted without a second lookup.
- `GET /api/status` → `caller` shows the switches and counts what the door refused, would have refused, and kept as a row (`typedKept`). It also counts the gate checks where the hook named a registered agent and the board saw no agent behind the call (`noAgentSeen`, `lastNoAgentSeen`): on a machine where sessions run under another program name, that is where it shows.
- **In a pane, then confirmed on the board:** if the owner answered in a pane, **Mission Control** records it with `task.sh gate-approved N gK "<what was said, when>"` (or `--decline`). The gated agent can't record an answer for its own gate; it asks Mission Control.
  - **A recorded "yes" releases nothing.** It is a proposal. The gate stays pending, no grant is minted, and the agent is told not to retry yet. The gate's row quotes the record and who typed it, and the owner clicks **✓ CONFIRM · RUN ONCE** (now it is approved, as any board approval), **✕ DECLINE**, or **⚑ NOT WHAT I SAID** (the record is thrown out and stays on the receipt as rejected; the gate goes on waiting; Mission Control and the agent are told).
  - **The agent always hears "not approved yet".** That notice, and the one sent when you reject a record, cannot be replaced in the agent's queue by a later message. It is dropped only once you have decided, so it never arrives after the approval.
  - **Why:** the record is typed by an agent, and the name it gives is one it declares for itself. An approval that rested on it would be an approval an agent could write.
  - A recorded **decline** takes effect at once: it only reduces what runs.
  - `SETTINGS.paneAnswers: 'direct'` restores the behaviour before 1.2, where the record was the approval. The default, also when the key is absent, is `'confirm'`.

A chat message never approves. Neither does anything the agent itself sends: a `gate_decide` request that carries an agent or intake identity is refused, decision token or not. The same goes for the request behind NOT WHAT I SAID.

**Verified 2026-10-31** (pilot, task #343): an approved gate runs with no further prompt in both **acceptEdits** sessions and **auto-mode** workers. The hook's `allow` is honoured by Claude Code's permission system and its auto-mode check alike.

## What is gated (default policy)
The policy is `policy.json`: `overlay/policy.json` for your own rules, else `examples/policy.json`. `POLICY.md` carries a generated, human-readable block of it (`node scripts/policy-render.mjs --write POLICY.md policy.json`; a test fails when the two drift).

| class | gated | free |
|---|---|---|
| merge *(standing)* | `gh pr merge` (the row names the PR: title, branches, repo) | `gh pr view/list/create`, `--help` |
| push | `git push` to `main`/`master`, `--force`/`-f`/`+ref`, tags, `:ref` deletes, any push to a `@publicRemotes` or `@deployOnPush` repo. The repo is every **push** address of the remote (its `pushurl`s and push rewrite rules included; with no repository named, the remote git picks: the branch's `pushRemote`, `remote.pushDefault`, the branch's `remote`, then `origin`), or the address the call itself gives the remote: `-c remote.<name>.url|pushurl=…`, `--repo=…`, a `git remote add|set-url` earlier in the same call. A call that changes a remote another way is asked: `-c url.…`, `GIT_CONFIG_*` variables, `--config-env`, `git remote rename|remove`, `git config remote.…|branch.…|push.…`, `-c branch.…|push.…`, a `git switch`/`checkout`/`branch -u` before a push that names no repository, or a repository or address the gate cannot read (a variable or a substitution) | feature branches, `checkpoint/*` |
| deploy | `vercel` (not `ls/whoami/logs/inspect/env ls`), any `launchctl` load/unload/kickstart of a `@paidOrOutbound` label, `shopify deploy/push/publish` | — |
| deploy-local *(standing)* | `launchctl bootstrap/bootout/load/unload/enable/disable` of any other label (a service on this machine) | kickstarts, `launchctl print` |
| upgrade | `zulu upgrade` / `zulu rollback`, `scripts/upgrade.mjs` (any form), `install.sh upgrade` / `rollback`: an agent upgrading or rolling back the install it runs in. Never covered by a program go. | the `--check` form, `zulu doctor` |
| env | `gh secret set/delete`, `gh variable set/delete` | listing |
| guarded | any run of a script on `@guardedScripts`, for scripts that write without a flag (e.g. a theme updater) | runs with a `@dryFlags` flag (`--dry-run`, `-n`, `--check`, `--plan`) |
| write | a script run with `--commit --apply --write --execute --confirm --activate --live --send --go`: **dry run first** | the same script without the flag |
| outbound | `curl` POSTs to chat/SMS/email-send APIs; MCP `…send_message/reply/forward` | drafts, GETs |
| store | MCP Shopify mutations, `create-*`, `update-*`, `set-inventory`, `bulk-*`, … | MCP reads and queries |
| delete | `rm -r` outside the git working tree the command runs in (anywhere, if it runs outside a repo; or on a glob/variable/`~` path), `DROP/TRUNCATE` via SQL tools, `gh repo delete` | `rm -rf build` inside the repo; the agent's own scratch space (`/tmp/claude-*/…`, `$TMPDIR/claude-*/…`, also via a variable assigned in the same command) |
| schedule | `crontab` (not `-l`), writing `~/Library/LaunchAgents/` | reading them |
| self | reading `data/guardrails/**` or the decision token; writing `policy.json` (in the live checkout or any git worktree of the repo), `~/.claude/settings.json`, `~/.codex/hooks.json`; a command that can send (`curl`, `wget`, `node`, `python3`, `osascript`, …) and contains `gate_decide`; an agent running `task.sh gate …` | reading your settings; `grep`/`cat`/`sed` of the gate's own source |

**Help is free:** `--help`, `-h`, `--version` and `help` on a gated program (`gh`, `git`, `vercel`, `launchctl`, `shopify`, `crontab`) print usage and change nothing, so they aren't gated. That never applies to scripts or to anything opaque.

**Where a command runs:** each command is judged in the folder it actually runs in. That means the hook's folder, then every literal `cd` before it in the same chain (a subshell's `cd` stays inside the subshell), then `git -C`. So `cd /elsewhere && rm -rf build` is judged in `/elsewhere`, and `git -C ~/site push` checks `~/site`'s remote. `chdir` and `cd -- <folder>` count as a `cd`, and `pushd -n` changes no folder. A `cd` counts for certain only when nothing but `&&` joins it to the command, because a failed `cd` then stops the command. After a `;`, `||`, a pipe, `&`, a condition or a `popd`, the command is read in every folder it may run in (with each change, and without the ones that may have failed), and it is held if any of them holds it. Such a row names those folders, and the gate reads no repository for it. When git is told its repository (`--git-dir`, or `GIT_DIR` on the command or exported earlier in the call), its remotes and branch are read there. After a `cd` the gate can't resolve (`cd "$X"`, `cd -`, a `cd` with extra words, `pushd +1`), path- and repo-dependent rules ask instead of guessing.

**Which branch a push sends:** a push that goes through the current branch (no branch named, `HEAD`, `@`; under `push.default upstream` also the branch's upstream name) is judged by the folder's branch AND by the branch any earlier `git switch`, `git checkout <branch>`, `checkout -b|-B`, `switch -c|-C`, `stash branch` or `rebase <upstream> <branch>` in the same call names (also inside a command string or a script body handed to a shell, `sh -c "git switch main"`), and is held if any of them is protected. A push inside such a body is judged with the switches that stand before the shell command too (`git switch main && bash -c "git push origin"`). A command substitution (`$(…)`, backticks) is read apart from the rest of the call, so a switch inside one counts for every push in the call, and a push inside one is judged with every switch in the call. Nothing is ever removed from that set: on `main`, `git switch -c feat && git push -u origin` stays held as before; name the branch (`git push -u origin feat`) to push it freely. A switch the gate cannot read is asked: `-`, `@{-1}`, `--detach`, `--orphan`, `--track`, an option it does not read to the end (git takes any unambiguous shortening, so `--mov` is asked), a tag or a commit, a name with a variable, glob or brace, `gh pr checkout` (and `gh co`), `git branch -m`, `git symbolic-ref`, `git bisect`, and any git or gh subcommand the gate does not know (an alias such as `git co` may switch). Under `push.default upstream` a bare push after a switch, a branch made, `git branch -u`, or a `git pull` or `git fetch` with `--set-upstream` in the same call is asked (the call may set the upstream); under `push.default matching`, or with a push refspec configured for the remote, a bare push sends more than the current branch and is asked. Not read: a switch inside a script or program the call runs (`./x.sh`, `npm …`); HEAD written directly (`echo "ref: refs/heads/main" > .git/HEAD`); a switch that stands after the push in the text but runs before it, in a loop (`for b in x main; do git push origin; git switch $b; done`) or in a function defined earlier and called later; and a switch handed to `env -S "…"` as one string. A push after any of these is judged by the folder's branch as read before the call. After `git worktree add` and a `cd` into the new folder, the folder does not exist yet when the gate reads it, so the push is asked as one with an unknown current branch.

**Opaque:** if a command mentions a gated action and the gate can't read it with certainty, the whole call is gated as `opaque`. Examples: `$BIN pr merge`, `eval …`, `… | sh`, `xargs gh pr merge`, an interpreter heredoc that runs `gh`, an unterminated quote. The parser keeps one invariant, and tests pin it: every trigger hit is either attributed to a command it recognised (then gated or cleared) or the call is opaque. A hit is never dropped.

**Redirects and here-strings:** the word after `>`, `>>` or `<<<` belongs to that operator however it is written, so `bash <<< "gh pr merge 5"` is read as the command it runs and `echo x > "a b.txt"` writes that file.

**However a guarded file is reached:** the rule resolves the path, so `data/./<file>`, `data//<file>`, `cd data && cat <file>`, a call made from inside the folder, and on macOS `/System/Volumes/Data/<path>` are all the same file. The hook's fast path looks for a single guarded file by its bare name (at a path boundary: `webhooks.json` is not `hooks.json`) and for a guarded folder by its path, in the command or in the folder the call is made from; `/./` and a doubled slash are dropped before the match.

**A bare name routes, it does not decide.** A call that names `settings.json`, `hooks.json`, `config.toml` or `policy.json` in any repo starts the hook's Node step and one board check; the rules then read each command against the folder it runs in. A program handed to an interpreter (a heredoc, `node -e`) or text no command explains is held on such a name only when the text has the folder and the name side by side (`.claude/settings.json`), or the call runs in the guarded file's own folder (its own, or after a `cd`). So a script in another repo that opens `.vscode/settings.json` or fetches `…/webhooks.json` is clear. An interpreter's program run from inside a guarded folder is held whatever it names, because the rules cannot read what it opens there. Going into a write-guarded folder (`cd ~/Library/LaunchAgents`) is not a write; what is then written there is.

**Not read:** a glob (`data/mesh-dec*`) or a variable (`$D/<file>`) in a path, because the name is not in the text; a copy or archive of the folder above a guarded file (`tar czf x.tgz data`, `cp -R data /tmp/d`); and a file read out of git's own store (`git show HEAD:<path>`). For the decision token and the grants file, what stands behind that is the decision door (a decision is taken only from the board page, never from a session) and the files' owner-only mode.

**Letter case:** on a disk that ignores case (macOS and Windows by default) a path, a script name or a program name in another case is the same thing, and every rule reads it that way: `Overlay/POLICY.JSON`, `scripts/TASK.SH gate …`, `GH pr merge 5`. On a disk where case matters, names are compared exactly.

**Shell keywords:** the command after `then`, `do`, `else`, `elif`, `if`, `while`, `until`, `coproc` or `!` is read as a command of its own, so `if …; then gh pr merge 5; fi` is a merge.

**Checks (since 1.2):** more things the gate reads, each behind its own switch in the policy's `checks` object. A switch is `off`, `observe` or `enforce`; a missing key means `observe`.

| check | what it holds, as `opaque` | left alone |
|---|---|---|
| `inlineBodies` | code handed to an interpreter on the command line that mentions a gated action: `node -e` / `--eval` / `-p`, `python -c`, `perl -e`, `ruby -e`, `php -r`, `osascript -e`, `deno eval`, `bun -e`, `lua -e`, `Rscript -e` | a body with no gated word in it (`python3 -c "print('merge')"` after a `gh pr view`) |
| `renamedBins` | a program the rules do not know, or one run by path, whose first words are a gated action: `./mygh pr merge 5`, `mygit push origin main`, `wrangler deploy` | words later on the line (`git commit -m "push the fix"`, `kubectl -n deploy get pods`), plain tools such as `echo`, `cd`, `mkdir` |

| `selfProtect` | the gate protecting itself, under class `self` (and `delete` for the last): **writes** to the gate's own files in the live checkout (`@gateCode`: the hook, the classifier and service, the page; `@guardGate`: the agent directory, `data/local.env`, `data/tasks/`), to hook settings anywhere (`.claude/settings.json`, `.claude/settings.local.json`, `.codex/hooks.json`, managed settings), to shell and git start files (`~/.zshrc` …, `~/.gitconfig`, `.git/hooks/`, `.git/config`) and to cmux's session maps; `git config` that sets `core.hooksPath`, an alias, or anything `--global` / `--system`; `git update-ref` / `symbolic-ref` on `refs/remotes/`; `git remote set-url/add/rename/remove`; in the live checkout, git that can leave a gate file holding something that has not landed (table below); `kill`, `pkill`, `killall`, `launchctl kill/stop` aimed at the board; `git clean -x` / `-X` anywhere | reading any of them; the same files in a git worktree of the checkout; `git config` reads; `kill` of anything else; `git clean -fd`, `git clean -n…` |

**The live checkout and its worktrees.** A path written `<live>/…` in a list means the board's own checkout only. (`<repo>/…` means the checkout and every git worktree of it.) Work happens in a worktree and reaches the live checkout through a held merge, so an edit of `src/gates.mjs` in a worktree is free and the same edit in the live checkout is held.

**What counts as a write** for these paths: Edit, Write, MultiEdit and NotebookEdit; an output redirect (`>`, `>>`); and the target of a program that writes it (`cp`, `mv`, `ln`, `install`, `rsync`, `tee`, `sed -i`, `perl -i`, `rm`, `touch`, `chmod`, `truncate`, `dd of=`, `curl -o`, `wget -O`). For `rm` and `mv`, a folder above a guarded file counts. `cat`, `grep`, `node --check`, `git diff` and a copy *from* the file are free. Also a write: a recursive copy, a sync or an extract into the checkout or a folder that holds a guarded file (`cp -R`, `rsync`, `ditto`, `tar -x`, `unzip`), a `patch` that names no file, a redirect with no program in front (`exec > file`) and `>|`. `$HOME` and `$PWD` in a target are read as the folders they are; any other variable followed by a guarded file's name (`"$X/src/gates.mjs"`) asks. On macOS and Windows another letter case is the same file. A command on several lines, a heredoc included, is read like the one line the hook sends. Not read: a write made from inside an interpreter or a script, and, for the paths outside the checkout, a copy into the folder that names the file only in two pieces.

**git in the live checkout:**

| `git restore <paths>` and `git checkout -- <paths>` (from the index or HEAD) | `restore --source <commit>` and `checkout <commit> -- <paths>` naming a `@gateCode` file or a folder above one |

| `git rm` / `git mv` of other files | `git rm` / `git mv` of a `@gateCode` file; `checkout -`; `read-tree -u`; `bisect` |
| `status`, `diff`, `log`, `add`, `commit`, a `reset` that only touches the index, `--abort` | |

A git command that names the live checkout itself (`-C`, `--git-dir`, `--work-tree`, `GIT_DIR=`, `GIT_WORK_TREE=`) is judged as running in it. Pathspecs are read too: `:/`, `:(top)src/gates.mjs`, `'src/*.mjs'`.

Held anywhere, not only in the live checkout: a `fetch` or `push` whose refspec writes under `refs/remotes/`, `git config -f <file>` on a guarded config file, a write of `remote.<name>.gh-resolved` (the repo `gh` acts on when none is named), and `git -c core.hooksPath=…` or `-c alias.…` on any call.

Stopping the board also covers a pid looked up with `pgrep` when the pattern matches the board's process or command line, and `launchctl remove` of its label. Signal 0 (`kill -0`) only asks whether a process is there and is free.

**The bar for `enforce`** (what the check also reads, so that the free commands above stay safe):

- **The index and HEAD of the live checkout.** A free `stash` or `restore` writes out what they hold, so moving them is the write: `reset <commit>` in any mode or for some paths, `read-tree`, `update-index --cacheinfo`, `update-ref`, `symbolic-ref` with a new target, `replace`, `branch -f` / `-m` / `-M`, a `fetch` into the default branch or with `-u`. A `reset` that only unstages, `read-tree HEAD` and `update-index --refresh` stay free. Refs are shared with every worktree, so `update-ref` of `refs/heads/main` or `master`, of a ref under `refs/replace/`, or of a branch or tag named `origin/…` is held from any folder.
- **Another repo's index.** A git call whose work tree is the live checkout and whose index is not (`--work-tree`, `GIT_WORK_TREE`, or `--git-dir` / `GIT_DIR` from inside the checkout; on the command or exported earlier in the same call) is held unless it only reads. So is `checkout-index --prefix=<a guarded folder>/`.
- **Names git reads another way.** `checkout <word>` when only a remote has a branch of that name; a local branch or tag named like the remote's (`origin/main`) at the moment it is made and again at the `merge --ff-only origin/<default>` that would take it; `remote set-head` and `set-branches`; `fetch --refmap`; a `pull` of two branches; `--upload-pack`.
- **Settings for one call.** In the live checkout the commands that bring content in (`pull`, `fetch`, `merge`, `checkout`, `switch`, `restore`, `stash`, `reset`, `rebase` …) are free only with no `-c`, no `--config-env` and no `GIT_*` variable set. `git -c core.pager=cat log` and the like stay free.
- **Stored settings.** In the board's repo (the live checkout and its worktrees share one settings file) every `git config` write is held except `user.*`; `git config --edit` too. Direct writes to `.git/HEAD`, `.git/index`, `.git/refs/**`, `.git/packed-refs`, `.git/info/**` and `.gitattributes` of the live checkout are on `@guardGate`.
- **Writers that name no file.** A pattern or a variable as the source of `cp`, `ln` or `install`; a download named by its address (`curl -O`, `--remote-name-all`, `--output-dir`, a bare `wget`, `wget -P`); `gunzip`, `gzip`, `bzip2`, `xz`, `zstd`; `cpio -i`, `pax -r`, `7z x`, `bsdtar`, `unrar`; `ex`, `ed`, `vim -es`. Each is held when the folder it writes into holds a guarded file.
- **Other spellings of a target.** `"$(pwd)/…"`, `` `pwd`/… `` and `~name/…` are read as the folders they are. A target with a variable, braces or a pattern (`src/$F`, `src/gates.{mjs,bak}`, `src/gate?.mjs`) is held when its fixed part reaches a guarded file or a folder that holds one.
- **Stopping the board, the rest.** `pgrep -u <user>` or `pidof` in a `kill`; `ps … | grep … | awk … | xargs kill` when a filter matches the board (or there is none); `fuser -k <port>/tcp`, `kill-port <port>`; the process group (`kill -- -<pid>`); a pid in `$(( ))` or in a variable set in the same call; `pkill -u` / `-U` / `-t` with no pattern; `reboot`, `shutdown`, `halt`, `launchctl reboot`, and a restart asked of the system through `osascript`.

Still not read, and left to the script-content check and the integrity card: a folder that reaches the command through a variable set elsewhere (`cd "$X" && …`, `GIT_WORK_TREE=$X`), `eval`, a pid read from a file, and a write made from inside a script. For the paths outside the checkout, a pattern is only seen when the call also names the file (the fast path looks for the name).

So the update after a landing stays one free command: `git pull --ff-only --autostash`. The same commands in a worktree are free. After a `cd` the gate cannot resolve, a session that started in the live checkout is judged as still in it.

- In `off` and `observe` the hook answers exactly as it did without the check. That holds for the check's fast-path lines too: a line that only an observing check adds sends the call to the board and gives the reading below, and never holds a call by itself (an interpreter's program or an assignment that names one of the check's paths passes, as with the check off).
- `observe` also writes one line per call that the check would have held: `"wouldHold": "<check>"` in `data/guardrails/observed.jsonl`, a ticker line and a `would hold:` line in the server log. Nothing is written to a task.
- `enforce` holds the call like any other opaque command. Changing a switch is an edit of the policy file, which is a `self` gate.
- What a check still cannot read: text put together at run time (`'pr mer' + 'ge'`), and a script file (a later check reads those).
- A rule in the policy belongs to a check when it carries `"check": "<name>"`: it then applies only while that check is `enforce`, and is what `observe` reports.

**Replay before you switch.** `node scripts/gate-replay.mjs` runs the classifier over the checks the board has recorded (`data/guardrails/checks.jsonl`) and prints what the checks would newly hold: a count per check and per agent, with samples. It only reads. `--since 7d`, `--check <name>` and `--json` narrow or reshape the reading. Two limits: a call the fast path passed left no line, so it is not counted, and lines recorded before 1.2 were cut at 160 characters, so their reading is approximate (the tool says how many).

**Dry run first** (`requireDryRun`, class `write`):
- The write form is refused (`run the dry form first: python3 scripts/archive.py`) until that exact command without its write flag has **run to completion** by the same agent, after the last time the write form ran.
- The first refusal also adds the script to the hook's watch list, so its dry runs are recorded from then on.
- A dry run chained into the write in one call (`x.py && x.py --commit`) never counts.
- The approval row shows when the dry run finished.

## Standing approval: a program go
Approving every merge after you've already said "go ahead with this" is noise. So one approval can cover a whole task:
- **Asking:** the agent runs `task.sh approve-request N --policy "<what the program is>" --program`.
- **Granting:** you approve it on the WORK panel. An answer you give in the pane can be recorded with `task.sh approved-in-pane N "…"`, and that record starts nothing: your row quotes it, and the go begins when you click **✓ CONFIRM** there.
- **What it covers:** gates of a **standing** class (`"standing": true` in `policy.json`) run **at once** on that task, with no tap, and each one still leaves a receipt: `GATE g3 auto-approved under program go go1 · merge · gh pr merge 41 …` plus a ticker line. By default the standing classes are:
  - **merge**, but only into a repo that GitHub confirms is **private** and that is in neither `@publicRemotes` nor `@deployOnPush`. If the repo is unknown or unconfirmed, the merge asks per action.
  - **deploy-local**: loading or unloading a service on this machine (not a `@paidOrOutbound` one).
- **Which repo a landing targets:** the board has to be sure, or it asks you.
  - **The landing must be its own command.** Under a program go, `gh pr merge …` runs by itself only when it is the whole command. A leading `cd <folder> &&` is fine, and so is a plain `GH_REPO=<owner/name>` in front of the call. Anything else in the same text (another command, a pipe, a redirect, any other mention of `GH_REPO` or `GH_HOST`) asks you, and the agent is told to run the landing as its own command.
  - **Every repo the command names must agree:** the repo flag in any spelling (also inside a group of short flags, `-sR <repo>`), a pull request URL, and each `GH_REPO=` assignment. One repo on github.com is the target. Two different names, a name the board cannot read, or another host count as unknown.
  - **The words are read as `gh` reads them.** A flag that takes a value (`-t`, `-b`, `-F`, `-A`, their long forms, `--match-head-commit`) takes the next word, whatever it looks like, so a repo flag or an address placed after one is only that flag's text. A flag the board does not know, or `--`, counts as unknown. `--admin` always asks.
  - **Nothing named:** the target is the checkout's origin, but only when every remote of the checkout and every `gh-resolved` key point at that same repo (gh picks its base repo from all of them, and a remote named `upstream` wins). Otherwise it is unknown.
  - A `GH_REPO` already set in the agent's shell before the call is not visible to the board.
- **What it never covers:** production deploys, secrets, store writes, sends, protected or public pushes, deletes, schedule changes and the gate itself always ask per action.
- **How it ends:** you revoke it with **⊘ REVOKE GO** on the task's row, or the task owner runs `task.sh revoke-go N`. It also ends when the task closes. It never carries over to another task.

## Which task a gate lands on
1. The agent's **focus**. `task.sh focus N` sets it by hand. `task.sh claim|start N` sets it too, but never over a focus the agent set by hand on a task that is still live.
2. Else its single live task.
3. With **no** live task, a new task `GATE: <class> — <command>` owned by the agent. An unregistered session's gate lands on mission control.
4. With **two or more** live tasks and no focus, the call is refused: `set it first: task.sh focus <N>`. The receipt must land on the right task.

## Fail closed
| condition | a gated call | anything else |
|---|---|---|
| board down or slow | **denied** ("board unreachable — fail closed"). The hook decides locally from the policy file, honoring `mode` and `enforceFor` (it looks the agent up in the mesh directory), so an observed agent isn't blocked. Which agent it is comes from the session the hook runs under (the workspace of the topmost agent process above it), not from the id in the hook's own environment, so a child session started with an observed agent's id is still enforced. An agent it can't identify is treated as enforced. Each request carries the hook's deadline, so a board that only gets to it later (frozen, overloaded) drops it instead of filing a gate nobody was told about | untouched |
| the Node step prints nothing | **denied**: "not gated" must be said explicitly (exit 3), so silence is never an allow | untouched |
| the call's own text names a hook event (in a command, a comment, a tool's input) | answered like any other call. Which event this is comes from the parsed input in the Node step. The shell reads it only when the Node step could not answer, from the input's own key in a form a string value cannot produce, and only when that key occurs once | untouched |
| the Node step has not answered after 12 seconds | **denied** by the hook script itself ("the gate check did not answer in 12 s"). Claude Code lets a call run when a hook answers after its registered time limit (15 s; seen on 2.1.321), so the script never waits that long: the Node step gives up on the board after 8 seconds, and the script gives up on the Node step at 12 | a call after the fact (PostToolUse) ends with no output |
| the session's environment names another board (`MESH_BOARD` or `MC_PORT` set to something that is not this checkout's board) | **denied**, and the reason names both addresses. Nobody is asked: not that address, not the board. The hook takes the board's address from the checkout's own `data/local.env`, else the default port, never from the environment | passes, judged by the hook itself as when the board is down |
| the policy's fingerprint version changes (an upgrade) | a gate filed before it and approved after it still runs that exact shell command: the board re-fingerprints it from the stored text at approval | — |
| `policy.json` invalid | the last good policy, else the shipped default; the card turns red | untouched |
| the hook's Node step fails | **denied** ("the gate check failed") | untouched |
| trigger file missing | the shipped default triggers (`scripts/gate-triggers.default`) | untouched |

**The hook does not believe the session's environment.** A settings file's `env` block reaches every hook process of the sessions in that folder (seen on Claude Code 2.1.321), a running session's included. So the hook script puts the system folders first on `PATH` before it runs anything (`cat`, `sed`, `dirname`, `sleep`, and the `git`, `ps` and `lsof` its Node step starts are the system's own), clears the variables that make a shell or Node load other code (`NODE_OPTIONS`, `NODE_PATH`, the `DYLD_` and `LD_` loader variables, `BASH_ENV`, `ENV`), and takes the board's address from the checkout it belongs to. Its Node program is the one the registered command names: the installer writes `GATE_NODE='/…/node'` in front of the script, and an assignment on the command line beats a settings file's `env` block. If the hook is registered without that path, the script does not look `node` up on the session's `PATH`: a call that reaches the Node step is denied, and the reason says to run the installer again. `GATE_TIMEOUT_MS` can shorten the wait for the board and cannot lengthen it. If you export `MESH_BOARD` in your shell for the command-line tools and it names a board other than the one this hook belongs to, gated calls in sessions started from that shell are denied until you unset it or make the two agree.

**Speed:** a call that hits no trigger never starts Node. The hook greps the call against `data/guardrails/triggers` (generated from the policy, plus watched scripts) and exits in a few milliseconds; the tests hold the median under 35 ms (on shared CI runners, which spawn processes 2–3× slower: under 150 ms and faster than starting Node). Only a hit asks the board.

**The fast path is tested on the real hook JSON.** A trigger matches the JSON Claude Code actually sends, where a word or flag that ends the command is followed by `",` or `"}`. It doesn't match a tidied-up copy of the command. The tests send every gated sample, with the action at the end and in the middle, in each field order, through the real `gate-hook.sh`. The hook uses the system `grep`, and a grep error counts as a hit.

**Every check is logged:** each answer the board gives (pass, allow, deny, observed) adds one line to `data/guardrails/checks.jsonl`: time, agent, tool, decision, task/gate, and a 160-character excerpt with secrets withheld. A call that ran ungated but appears there was passed by the board; a call that's missing never reached it.

## Crash and restart
An approval runs **at most once**, even if the board dies mid-call. The board lets a gated call through only when `grants.json` holds an **unspent** grant for exactly that call and agent. A missing, corrupt or unreadable grants file reads as "no grant": the call is refused and becomes a new gate. Lost state can only make a run less likely, never more. The file is replaced atomically (a temp file, then a rename), and a leftover temp file is never read.

Redeeming takes two writes: the grant is marked spent, then the ledger gets the receipt. The hook lets the tool run only on an `allow` it actually received. So for a crash:

| the board dies… | the hook gets | what ran | the next attempt |
|---|---|---|---|
| before the grant is marked spent | no answer → **denied** | nothing | allowed once (this is the first run) |
| after the grant is spent, before the receipt | no answer → **denied** | nothing | **a new gate**; the owner is asked again |
| after the `allow` was sent | allow | the command, once, in the agent's process | **a new gate** |

**Startup reconcile.** In the middle case the task's receipt is left at *approved*. When the board starts, before it accepts any request, it compares spent grants with the ledger. A gate still marked approved whose grant was spent gets its receipt, stamped with the time the grant was spent and noted `recorded after restart; outcome unknown`. The board can't tell the middle case from the last one, so it doesn't guess. A grant that expired unused gets an `expired` receipt the same way. Running it again changes nothing, and it never wakes an agent. The board log says how many spent grants it checked when there was nothing to repair.

The tests in `test/gate-crash.test.mjs` cover this: a real process killed between the two writes, a normal run and then a restart, torn and corrupt grant files, and concurrent attempts at one approved call (exactly one is allowed).

## The receipt chain

Receipts on a task are plain JSON, so an edit to one would not show by itself. Since 1.2 every change to a gate (requested, approved, declined, released, expired) also appends one line to `data/guardrails/receipts.jsonl`: `{ seq, at, task, gate, event, digest, prev }`. `digest` is a hash of the gate's decision fields and `prev` is the hash of the line before, so the lines form a chain. The running board keeps the chain's head and an index of it in memory.

- **Check it:** `task.sh audit N --verify` recomputes the chain and compares it with the task's gates. It exits 1 and lists each difference: an edited receipt, a line removed or changed, a file that ends before the head the board holds. The `guardrails` card runs the same check over every task at start and every six hours, and goes red on a difference.
- **A grant runs only with its approval in the chain.** When an approved call comes back, the board lets it run only if the chain holds an approval for that task and gate that this board recorded, not yet followed by a release. A grant and a task record written by hand have no such line, and a line added to the file by hand is not in the running board's memory. The call is refused, the gate is marked `disputed`, the card goes red and the task gets a comment. Asking again files a new gate.
- **Only a decision writes an approval line.** The chain writes `approved` only for the write that was the decision on that gate: your click, a pane answer the ledger accepted, or a program go's own run. If a task record is edited to read approved and some other write then touches the task (a comment is enough), the board records that as `changed-outside-decision`: it never counts as an approval, `audit --verify` lists it, and the card stays red.
- **A failed write never blocks a gate.** If the line cannot be written (a full disk), the gate event still happens, the line is kept in memory and written with the next one, and the card is amber until then.
- **Limits.** This makes an edited receipt show and makes a hand-made approval fail on the running board. It does not stop someone who rewrites the whole file and the task records and restarts the board. Nor does it stop a line appended by hand with matching hashes followed by a restart: the board rebuilds its index from the file. The daily state backup carries the file, which is where you would compare.
- **First start and errors.** The first start writes a `started` line, then adopts only approvals that are still in flight (approved and not yet expired). Gates settled before that line are not expected in the chain. If the chain file exists and cannot be read, the board adopts nothing, starts no new sequence, refuses approved calls and shows the card red until it can read the file.
- **Switch:** `SETTINGS.receiptChain` (`on` by default; `observe` writes lines and only reports what it would refuse; `off` writes nothing).

## The gate checks itself
Agents run as your macOS user, so they *can* change the gate's files and the settings that register its hook. Two parts make sure such a change is stopped where it can be and is never unseen. Neither needs `sudo`.

**Gate integrity, on the guardrails card** (`SETTINGS.gateIntegrity: { mode: 'on' }`; off until you turn it on). Every poll the board checks the following. It only reads.

- **The gate's files.** The hook, the classifier, the board's page and the other files on the policy's `gateCode` list, as they are in the checkout the board runs from, are compared with what has landed on the remote's default branch (a release install: with the release tag it is on). The board asks the remote itself and keeps the answers in `data/gate-integrity-state.json`, so moving the local tracking ref hides nothing.
  - **current:** green.
  - **behind:** a change has landed and this checkout has not been fast-forwarded yet. Amber, then red once it has been behind for `behindMinutes` (default 30; `0` = never red for being behind).
  - **changed:** a file matches neither what has landed nor the landed commit this checkout is on, or the checkout was moved back to an older commit. Red at once, on the alert ladder, and the card names the files.
- **The hook's registration.** The user settings file must run this checkout's hook with the exact command the installer wrote and a matcher that covers every tool. The Node path in front of the script, as an absolute path, is part of that: without it the hook's Node step would be whatever `node` the session's `PATH` names first, and the card says to run the installer again. A file that only mentions the hook does not count. The Codex hooks file is checked where the hook was installed.
- **Settings files that turn the gate off or steer it.** In the user settings file, and in `.claude/settings.json` and `.claude/settings.local.json` of every registered agent's repo: `disableAllHooks`, or an `env` block that sets one of the gate hook's own variables (the board's address or port, the hook's wait, its Node, its identity, its folders). Red, with the file's path. The value is never shown.
- **The triggers file** the hook greps first must equal what the policy generates. If it does not, the board rewrites it and says so.
- **The port** in `data/local.env`, if set, must be the board's own.

**The settings-change hook** (`scripts/gate-config-hook.sh`, installed by `guardrails-install.sh` next to the gate hook). Claude Code reads its settings files again while a session runs, and a project file can switch off a hook the user file registered. This hook runs when a settings file changes under a running session. It blocks the change for that session when any settings file the session reads would switch hooks off, steer the gate hook through `env`, or drop the gate hook from the user file. The board gets a red ticker line. The hook decides by itself, so it blocks with the board down too. Until you run the installer again the card says `settings-change hook not installed`, without changing colour.

What it was seen to do, and where it stops (Claude Code 2.1.321, headless sessions in scratch folders):

- **A blocked change stays out and every hook keeps running.** That holds when the changed file is the one that registers the hooks.
- **While the offending file is on disk, no settings change passes for that session.** A change that is let through makes the session read all its settings files again, and the blocked one would come in with it. Put the file right and changes pass again.
- **It answers "blocked" itself after 8 seconds** if its check has not finished. A hook that answers after its registered time limit lets the change apply, so silence must never be the answer.
- **It does not believe the session's environment.** A settings file's `env` block reaches every hook process. The script puts the system folders first on `PATH`, clears the variables that make a shell or Node load other code, and takes your home folder from the account record.
- **It does not help a session that starts in a folder whose settings already switch hooks off.** That session never runs the hook. The card's scan is what shows the file.
- **It cannot block managed policy**, and it reads a file a moment before Claude Code does, so a second write in that instant would get past it. The card does not depend on timing.
- **A settings file a session is started with is not read by either part.** Claude Code takes a settings file on its command line (`--settings`), and cmux starts its sessions that way. That source ranks above your own, the project's and the local file, and its `env` block reaches hook processes too. Neither the card's scan nor this hook looks at it yet.
- **Not tested:** the user settings file as the changed file, and interactive sessions.

Only Claude Code's managed settings, which need administrator rights to write, keep a hook from being switched off at all.

## Install
New here and want only this? [QUICKSTART-GUARDRAILS.md](QUICKSTART-GUARDRAILS.md) installs the board and the hook in five steps (`./install.sh --guardrails`). On an existing install:
```bash
scripts/guardrails-install.sh                  # show what would change
scripts/guardrails-install.sh --apply          # Claude Code: ~/.claude/settings.json (backed up first)
scripts/guardrails-install.sh --apply --codex  # also Codex: ~/.codex/hooks.json
scripts/guardrails-install.sh --remove --apply [--codex]
```
Run it yourself: changing these files from an agent session is itself gated. The installer writes three entries for Claude Code: the gate hook before and after a tool call, and the settings-change hook ([the gate checks itself](#the-gate-checks-itself)). Claude Code reads its settings again while a session runs (seen for project files on 2.1.321), so a running session may pick the hooks up by itself; to be sure, restart the session or review `/hooks` after installing.
- **Codex:** hooks need Codex's `hooks` feature (stable in current releases). Codex also asks you to trust a new hook once. Sessions launched through cmux's Codex wrapper already run with `--dangerously-bypass-hook-trust` for the hooks cmux injects; check that a Codex pane is actually gated before you rely on it.
- **Codex: which folder a command runs in.** Codex runs a shell command in a folder of the model's choosing (the tool's `workdir`), but tells the hook only the command and the session's folder (checked on Codex 0.162.1). So the gate never reads a repository from the session's folder for a Codex shell call. A folder counts only when the command names it from the root and it certainly applies: `git -C /abs/path …`, or `cd /abs/path` joined to the command by `&&` alone. **Every held Codex shell call whose folder is not named that way is refused without a row**, unless it is a `gh` call that names its repository. The agent is told to run it again with its folder in the command (`cd /abs/path && …`, `git -C /abs/path …`, `gh … --repo owner/name`). That call is read and, if it needs you, asked as usual. So the folder on a Codex row is always where the call runs. If a later Codex sends `workdir` to the hook, it is used.
- **Your own `!` commands:** in Claude Code, a line you type with `!` runs outside the model's tools, so it is not gated. That keeps you able to act when the board is down.

## Rolling out
- **`mode: "observe"`**: every gated call is logged ("would wait on the owner", ticker + `data/guardrails/observed.jsonl`) and nothing is blocked or written to tasks.
- **`enforceFor: ["agent-a", "agent-b"]`**: enforce for a pilot group while everyone else observes. Read the observe log for false positives, then set `enforceFor: ["*"]`. That edit is itself a `self` gate.
- **`"*"` means every *registered* agent**, i.e. a session in the mesh directory (a cmux workspace). A Claude or Codex session with no mesh identity is only observed, unless `enforceFor` also lists **`"unregistered"`**. Its gates then land on a new task owned by Mission Control. This keeps your own sessions outside cmux from being gated by the fleet flip unless you ask for it.
- **Which agent a call belongs to.** By default the hook says which workspace it runs in, and the board takes its word. With `SETTINGS.callerEvidence.mode: 'on'` the board works it out from the process behind the hook's call: the agent session at the top of its chain (see [SECURITY-MODEL.md](SECURITY-MODEL.md), Sender names).
  - A child session started with another agent's workspace id is judged as the session that started it. Before, that id alone could turn an enforced agent into an observed one.
  - A lookup that fails, or a cmux session the board cannot name, is enforced whatever it declared. The check log marks it `enforcedUnknown`.
  - A session outside cmux is still `unregistered`. Use `defaultMode: "enforce"` if those must be held too.
  - The check log (`data/guardrails/checks.jsonl`) keeps the declared name beside the real one as `declared` whenever they differ.
- **`defaultMode`** decides what happens to a session nobody listed.
  - `"observe"` (the default, also when the key is absent) is the opt-in behaviour described above.
  - `"enforce"` turns it around: every session is enforced, registered or not, a newly registered agent included, except the names in **`observeFor`**. `"unregistered"` in `observeFor` covers every session with no identity. `enforceFor` is then not read.
  - **Take readings before you switch.** While the default is `observe`, each observed call that `enforce` would have held gets `"wouldEnforce": true` in `data/guardrails/observed.jsonl`, `[would enforce by default]` on its ticker line, and a `would enforce:` line in the server log. Read two days of them, put the sessions you want left alone in `observeFor`, then set `defaultMode`. That edit is a `self` gate.
- **Headless runs the board starts** have no workspace. The launcher exports `MESH_GATE_IDENTITY` (`triage` for the triage pass, `dispatch` for a session started from a card) and the gate knows the session as `headless:triage` or `headless:dispatch`. A registered workspace always wins over this. `"*"` in `enforceFor` does not cover a headless run; name it, or use `defaultMode: "enforce"`. Its gates land on a task Mission Control owns. With the board down the role is ignored and the session is enforced, as any unknown session is.
  - **Never put a headless role on `observeFor`.** The role is an environment variable, and any session without a workspace can set it. A role on the observe list would be a way out of enforcement for every such session. If a headless run must not be held, change what it is allowed to run, not the list.
  - **With `callerEvidence.mode: 'on'` the variable is ignored.** The board names a headless run from things a session cannot set. For a scheduled pass it is the launchd job that started the process: list it in `callerEvidence.jobs`, for example `{ "<prefix>.mission-control-triage": "headless:triage" }`. For a session started from a card it is the workspace the board itself opened. A job you did not list is an unregistered session.
- **The owner's signed form is yours alone.** `task.sh`, `agent-send.sh` and `mesh-cli.mjs` with `--signed` attach your decision token, so the message or comment counts as yours. In the shipped policy an agent that runs one of them with that flag is held (class `self`). Your own typed lines are never held, because hooks fire only on an agent's tool calls. If you keep your own policy file, copy the three `--signed` rules into its `self` class.
- **`mode: "off"`**: the hook passes everything.

Board card **`guardrails`** (infra):
- **amber**: a gate waiting more than 30 min, or the hook missing from the agents' settings;
- **red** (alert ladder): an invalid policy.

## Writing rules
Each class has `id`, `label`, optional `requireDryRun`, `ttlMinutes`, and `rules`. A rule matches one simple command (or tool call) with:
- `bin` (basename) + `args` (a prefix of the positional words) / `argsAny` / `notArgs` / `flagsAny` (one-letter flags also match inside clusters such as `-rf`) / `unlessFlags`;
- `script: true` (an interpreter + script path, or an executable path);
- `scriptIn` (one glob or one `@list` of script files, e.g. `@guardedScripts`): the script is gated on every run. Behind an interpreter or a shell the rule is tried on **every** word that looks like a script, not only the first, so a flag's value in front (`node --import ./pre.mjs scripts/upgrade.mjs`, `bash --rcfile ./rc.sh install.sh upgrade`) does not hide it. The rule's `args` are the words after the script that matched. A listed script named as an argument of another script (`node other.mjs scripts/upgrade.mjs`) is asked too: the gate cannot tell an argument from a script there, and asking is the safe side. For the same reason a quoted argument of an interpreter call that ends in a listed script's path is asked.
  **The script on the program's input is a run of it too:** `node < scripts/x.mjs`, `cat install.sh | bash -s upgrade`, `bash -s upgrade <<< "$(cat install.sh)"`. It is read as the plain form (`node scripts/x.mjs`, `bash install.sh upgrade`) by the rules that name a script and by the rules on a flag, when the call names no script or program of its own; with one (`node x.mjs < data.json`, `bash -c … < file`) the input is data.
  **Interpreters and shells by any name:** a versioned or packaged name (`python3.13`, `pythonw`, `pypy3`, `node22`, `nodejs`, `bash5`, `zsh-5.9`) is read as the plain one, and `csh`, `tcsh`, `ash`, `mksh` and `rbash` as shells. **A `bin` rule's program run by its file:** when an interpreter or a shell is handed a script whose name is a program a `bin` rule names (`node /opt/homebrew/bin/vercel deploy --prod`, `bash bin/zulu upgrade`, `cat bin/zulu | bash -s -- upgrade`, and read in with `.` or `source`), the call is also read as that program. A shell's syntax check of such a file (`bash -n bin/zulu upgrade`) is held too. Not read: an interpreter whose name is in a variable or a substitution, a language the gate does not parse (`lua`, `tclsh`, `awk`), the script on a shell's input with its words before the file (`bash -s upgrade < bin/zulu`: the fast path does not route it), and a `bin` rule's program with its held word handed to `eval`, `xargs` or `watch`, or echoed into a shell (`eval "zulu upgrade"`, `echo upgrade | xargs zulu`, `echo "zulu upgrade" | bash`).
  **Not read as a run of the named script** (each is clear unless another rule holds it): the script read in with `source` or `.`; the script reaching the input any other way (through `head`, `sed` or another filter, or a substitution that is more than one file's content); an inline body that imports or spawns it (`node -e 'import("./scripts/x.mjs")'`; the `inlineBodies` check reads such bodies, see Checks); a package runner in front (`npx`, `npm run`, `pnpm exec`); and a copy or a link of the file under another name. A rule on a flag (`--commit`, `--apply`) does not depend on the file's name, so it holds a copy, a link and a package runner that carry the flag, and a pipe into a shell with the flag in the call is held as unreadable. A rule on a program is not affected by any of this;
- `method` + `urlAny` (curl);
- `tool` (a regex on MCP tool names; keep it to plain `.*` and alternation, because the hook greps it too);
- `sql`;
- `labels` (`@list`);
- `pathAny` (read or write) / `pathWrite` (a redirect, or any argument of a program that is not a known reader) / `pathGuard` (one or more globs or `@lists`; a write in the strict sense above);
- `mentions` (a word any argument must contain, case ignored);
- `textAny`;
- `when: "pushProtected" | "outsideRepo" | "gitConfigWrite" | "gitRefWrite" | "liveCheckout" | "boardProcess"`;
- `check` (the rule belongs to that check, see Checks).

`lists` hold your names (`paidOrOutbound`, `publicRemotes`, `deployOnPush`, `guardSecrets`, `guardConfig`), referred to as `@name`. `keywords` adds words that make an unreadable command opaque.
